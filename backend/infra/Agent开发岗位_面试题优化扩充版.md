# Agent 开发岗位面试题库

面向使用 Python、模型 API、工具调用、RAG 和任务编排构建业务系统的 Agent 开发岗位。包含原有 95 道题和新增 20 道工程题，以及 3 道编码练习和 2 个系统设计案例。

题目按“基础与最小实现 → 模型与工具 → 上下文与检索 → 可靠性与安全 → 协作与框架 → 评测与上线”的顺序排列，统一连续编号为 1—115。工程扩充题已融入对应主题，模型原理与训练知识放在附录。

- 第一轮：第 1—27 题，掌握 Agent 执行循环、模型使用、工具接口、记忆和上下文。

每题先用 30—60 秒讲核心回答，再结合展开部分补充实现步骤、具体例子与适用边界。常见追问附有简短参考回答，可用于口头演练；示例是设计说明，项目经历只填真实内容，未测得的效果不填写虚构数字。

每道主问题和编码、系统设计题均提供 100～300 字的面试回答示例，可先练习完整口述，再用核心回答和展开要点复习；常见追问保持简短参考形式。

题号以本版为准。可搜索题目关键词或使用内容导航定位；例如查找 `### 51.` 可定位幂等键设计题。

## Agent 基础与任务设计（第 1—9 题）

### 1. 什么是Agent？和大模型的本质区别？

**面试回答示例：** 我理解的 Agent 是一个围绕目标持续观察、决策和执行的系统，大模型通常承担理解与规划的工作，工具负责接触外部环境。例如处理退款请求，模型需要判断缺少哪些信息，再查询订单和政策，由业务代码检查退款资格，最后根据执行回执反馈结果。它与普通问答的主要区别在于能够形成行动闭环。实际设计时，我还会加入状态保存、权限校验、预算和终止条件，避免系统无限执行或误报成功。

**核心回答：** Agent 是围绕目标持续观察、决策并调用工具的系统；LLM 是其中可能使用的决策组件。

**展开要点：** 以客服退款为例，模型理解诉求并选择查订单、查政策等工具，应用维护任务状态、检查权限，必要时暂停等待审批。系统根据执行结果决定继续查询还是结束。因此介绍 Agent 时，应交代目标、可用动作、反馈来源和终止条件，而不能只说“LLM 加工具”。自主性越高，越需要明确可执行范围与失败兜底。

**常见追问：** 一次工具调用就算 Agent 吗？如何划定自主范围？

**追问参考回答：** 一次调用是否称为 Agent 取决于定义；面试中更应说明是否存在根据反馈继续决策的闭环。自主范围可以按工具白名单、金额上限、可访问数据和审批条件划定，由服务端执行约束。

### 2. Agent的基本架构有哪些核心组件？

**面试回答示例：** 我会把 Agent 架构拆成模型适配、工具执行、上下文管理、任务状态、控制循环和结果校验几个部分。模型负责提出下一步，工具层负责参数与权限检查，状态层记录当前进展，控制循环决定继续、暂停还是结束。例如查询失败时，需要保存错误信息再决定是否重试。各组件通过明确的数据结构交互，便于替换模型、定位故障和恢复任务。我的重点是让系统行为可追踪，关键业务规则由程序保证。

**核心回答：** 核心组件包括模型适配、工具注册与执行、上下文、任务状态、控制循环和结果校验。

**展开要点：** 可以把系统分成模型适配层、执行器和业务服务三层。模型适配层处理消息与工具协议；执行器处理调度、超时、重试与状态；业务服务完成订单、检索等真实操作。任务状态记录目标、调用结果、待审批操作和版本，日志用调用标识关联各步骤。这样能单独替换模型或框架，也方便复现故障。

**常见追问：** 不用 LangChain 如何实现这些模块？

**追问参考回答：** 用模型 SDK、工具注册表和循环实现决策，用数据库保存状态，用普通服务做业务校验，再接入日志与评测即可。LangChain 提供封装，但不是这些能力的必要条件。

### 3. Workflow、Agent 、tools 三者的区别。

**面试回答示例：** Workflow、Agent 和 Tool 分别解决流程组织、动态决策和具体执行的问题。Workflow 的路径主要由开发者预先定义，例如订单查询后进入资格校验；Agent 可以根据当前信息决定先查政策还是补问用户；Tool 则是查询订单等具体能力。实际系统通常会组合三者：外层用稳定流程控制权限和审批，局部让 Agent 处理不确定任务。这样既保留灵活性，也能控制成本、错误范围和执行结果。

**核心回答：** Workflow 用应用预设的控制流组织任务；Agent 由模型在允许范围内动态决定下一步；Tool 是可调用的具体能力。

**展开要点：** 例如“识别需求→查询订单→计算退款资格→人工审批→执行退款”可由 Workflow 固定控制；在查询阶段，Agent 根据缺失信息决定先查订单还是政策；查询工具只负责接收参数并返回数据。控制流、智能决策和具体动作分别有清楚职责，方便逐层测试，也能避免模型跳过审批直接执行写操作。

**常见追问：** 怎么避免把所有步骤都做成自由 Agent？

**追问参考回答：** 先把权限、金额计算、审批、持久化等确定性规则写入流程，仅开放需要语义理解或探索的步骤。每增加一个自主决策点，都应说明收益、允许动作和退出条件。

### 4. 什么时候用workflow什么时候用Agent?

**面试回答示例：** 我会先看任务路径是否稳定、规则能否明确表达。如果每一步输入输出和判断条件都清楚，例如报销审批，我优先用 Workflow；如果需要根据未知信息不断搜索、调整方案，例如跨文档调查，再考虑 Agent。也可以在固定流程中嵌入一个动态分析节点。选择时我会比较任务成功率、耗时、成本和维护难度，只有动态决策带来实际收益才增加自主性，并保留停止、澄清和人工接管机制。

**核心回答：** 流程稳定、规则明确时先用 Workflow；路径随环境变化、确实需要动态判断时再引入 Agent。

**展开要点：** 固定报表、表单审核和步骤明确的数据同步通常先做 Workflow；开放式调研、故障诊断等任务可能需要 Agent 动态选择信息源。选择时先建立简单方案基线，再观察失败是否来自路径无法预设，而非检索、数据或接口质量。如果是工具本身不可靠，增加自主决策通常只会放大问题。

**常见追问：** 如何证明 Agent 比固定流程更有价值？

**追问参考回答：** 在相同任务、工具和预算下比较固定流程与 Agent，观察完成率、人工介入率、成本及延迟。只有复杂或变化任务的收益能抵消额外工程成本，才有充分理由引入 Agent。

### 5. Agent的推理以及设计范式有哪些？

**面试回答示例：** 常见设计范式有 ReAct、先规划再执行、反思修正和层级协作。ReAct 适合边获取信息边决定动作，先规划再执行适合依赖明确的长任务，反思则用测试或证据发现问题并修正结果。例如生成分析报告，可以先拆成取数、计算、写作和核验，再根据数据结果调整计划。我不会为了复杂而叠加所有模式，而是先建立最小闭环，按任务特点增加规划和反馈，并设置明确的验收标准与执行预算。

**核心回答：** 常见模式包括 ReAct、Plan-and-Execute、反思修正及层级协作，重点是适配任务而不是堆叠模式。

**展开要点：** ReAct 适合根据工具反馈逐步探索；Plan-and-Execute 先形成任务清单，再执行和检查；反思模式针对结果提出修订；层级协作把子任务分给不同执行单元。计划应包含依赖、预期产物和完成标准。外部条件变化后允许局部修改计划，但限制重规划次数，防止系统始终停留在规划阶段。

**常见追问：** 计划失效时谁决定重新规划？

**追问参考回答：** 执行节点报告失败或新约束，控制器根据预设条件决定是否调用规划器。模型可以建议新计划，但应用负责检查预算、权限和任务依赖，避免擅自扩大目标。

### 6. 复杂任务怎么拆？

**面试回答示例：** 复杂任务拆解时，我会先明确最终交付物、限制条件和验收标准，再把目标拆成能够单独验证的子任务。每个子任务都要说明输入、输出、依赖和失败处理方式。例如市场分析可以拆成资料收集、数据清洗、指标计算和报告生成，其中计算依赖清洗结果，独立资料查询则可以并行。执行后根据实际观察更新计划，而不是把最初计划当成固定答案，同时控制粒度，避免大量低价值步骤增加协调成本。

**核心回答：** 先定义目标、约束和验收标准，再拆成有输入输出与依赖关系的子任务。

**展开要点：** 拆分时从验收产物倒推步骤，例如调研报告拆成需求确认、资料检索、事实抽取、章节写作和引用校验。为每步定义输入、输出、负责人、失败处理及版本，画出依赖关系；互不依赖的步骤可以并行。拆分粒度要让结果可检查，并保留必要上下文，避免子任务只得到模糊指令。

**常见追问：** 任务拆得太细有什么代价？

**追问参考回答：** 拆得太细会增加模型轮次、网络调用、上下文重复和结果合并成本，也可能丢失整体目标。优先以可独立验证的产物划分，而不是为每一个小动作创建 Agent。

### 7. 不用框架，如何实现最小 Agent Loop？

**面试回答示例：** 最小 Agent Loop 可以用普通代码实现：先构造消息和工具定义，调用模型，再判断输出是最终回答还是工具请求。对于工具请求，执行器校验名称、参数和权限，执行后按调用标识回传结果，然后进入下一轮。模型不能直接越过执行器操作业务。循环需要设置最大步数、超时和费用预算，遇到未知工具或异常时返回明确错误。只有结果满足验收条件才结束，执行记录也要保存，方便调试和恢复。

**核心回答：** 模型只提出下一步，执行器校验并执行工具，把观察结果写回消息，再继续直到完成或预算耗尽。

**展开要点：** 最小循环先准备消息和工具 Schema，调用模型后区分最终回答与工具请求。对工具名、参数、权限和预算逐项校验，执行后按调用 ID 回传结果，再进入下一轮。记录模型响应和工具观察，设置最大步数与超时。写工具还需要审批及幂等；模型适配器负责各供应商消息格式，控制循环不直接绑定单一 SDK。

**常见追问：** 模型输出 final 就一定完成业务目标吗？

**追问参考回答：** 不一定。final 只表示模型认为可以结束；退款、文件生成等任务还要验证账本状态、文件存在和内容要求。应由业务验收器决定成功、部分完成或失败。

**验证方式：** 用假模型验证一次调用、多个调用、未知工具和停止条件。

### 8. 如何处理重复调用、死循环和任务终止？

**面试回答示例：** 我会用多层限制处理重复调用和死循环，包括最大步数、总耗时、费用上限以及连续无进展阈值。重复检测可以比较工具名称、规范化参数和观察结果，但不能把所有重复查询都视为错误，例如轮询状态可能有业务意义。发现无进展后，系统可以补充信息、换策略、向用户澄清或终止。结束时应明确完成、失败或待确认的状态，并保留已经发生的操作，避免停止循环后仍让后台任务继续产生副作用。

**核心回答：** 同时设置步数、时间、费用与无进展阈值，检测重复行为后澄清、换策略或终止。

**展开要点：** 除限制步数外，还可以记录“工具名＋规范化参数＋结果摘要”，识别连续重复调用；记录已完成子目标，检测任务状态是否改变。遇到信息不足时优先澄清，而不是无限重试。终止原因应区分成功、预算耗尽、无进展、用户取消和执行错误，并保存已完成内容与可恢复状态。

**常见追问：** 如何判断新结果是否带来有效进展？

**追问参考回答：** 用任务相关指标判断：是否找到新证据、补齐必填字段、完成子目标或消除错误。相同参数再次得到相同结果通常没有进展，但轮询异步任务应另设间隔和总时限。

**验证方式：** 构造模型反复调用同一工具的样本，确保执行次数受限。

### 9. Agent的反思机制

**面试回答示例：** 反思机制的作用是根据反馈检查结果，再修正后续步骤。我会先确定检查对象和可信依据，例如代码用测试结果核验，报告用引用材料核验，然后让模型输出发现的问题、证据和修改动作。反思之后只重跑受影响的步骤，并限制轮数。如果只是让同一个模型无依据地再想一遍，可能重复原有错误。我会比较增加反思前后的成功率、额外延迟和成本，只有收益明确时才保留这一步。

**核心回答：** 反思机制用反馈检查结果并修正下一步，但需要明确的评判依据和停止条件。

**展开要点：** 反思应有检查对象和外部依据，例如用测试结果发现代码错误，或用引用证据检查报告结论。把“发现的问题、支持证据、修订动作”作为结构化结果，再只重跑受影响步骤。不要让同一模型无依据地反复自我评价；如果修订没有改善验收指标，应停止，并保留失败记录供人工处理。

**常见追问：** 如何评估反思的边际收益？

**追问参考回答：** 对同一组任务比较不反思、一次反思和多次反思，统计新增成功数、回退错误、额外耗时与成本。若后续轮次收益很小或引入新错误，就降低轮数或换成确定性检查。

## 模型选型、Prompt 与输出质量（第 10—14 题）

### 10. 怎么评测大模型能力？模型怎么选型？

**面试回答示例：** 模型选型需要从实际任务出发，先明确成功标准和安全、成本、延迟门槛，再建立代表性的评测集。Agent 场景我会重点比较工具选择、参数准确性、多轮稳定性、证据使用和拒答表现，而不只看通用榜单。例如客服查询和复杂报告可能需要不同能力，可以按任务路由。最终选择应基于相同输入和评分规则，同时记录失败类型及每成功任务成本，再通过小流量验证线上效果。

**核心回答：** 按实际任务选模型，先设效果、安全、延迟和成本门槛，再在固定数据集上比较。

**展开要点：** 先把岗位任务拆成问答、工具选择、参数生成、长文档处理等能力项，准备正常、困难及边界样本。固定 Prompt、采样参数和工具环境，比较完整任务表现，而不是只比单次输出。对高风险错误单独设门槛；上线前评估并发、限流及上下文长度是否满足实际业务。

**常见追问：** 如何同时比较质量与每成功任务成本？

**追问参考回答：** 先排除不满足质量或安全门槛的模型，再计算总调用费用除以成功任务数，同时报告成功率和延迟。对不同难度分层比较，避免便宜但频繁失败的模型看起来更优。

### 11. 怎么去写好Prompt?

**面试回答示例：** 好的 Prompt 应明确目标、输入背景、限制条件、输出格式和工具使用规则。我会把关键要求写得具体，例如缺少订单号时先澄清，查询不到数据时不能编造，并提供少量有代表性的正反例。对于复杂任务，还会说明验收标准和允许的步骤，但不会无限堆叠指令。修改后用固定样本比较结果，观察格式遵循、事实正确性和工具调用表现。权限、金额限制等硬规则仍放在程序中执行。

**核心回答：** Prompt 要说明目标、输入、约束、输出格式和工具使用规则，并用代表性样例验证。

**展开要点：** 一个实用 Prompt 可以包含任务目标、输入字段说明、证据使用规则、工具约束、输出 Schema 和少量正反例。把动态业务数据作为明确标记的输入，不与可信指令混写。先定位错误类型，再针对性修改，例如字段缺失补输出规则，事实臆造补证据要求；权限与金额限制仍由程序执行。

**常见追问：** 如何定位 Prompt 改动造成的回归？

**追问参考回答：** 保存改动前后的 Prompt 版本，固定其他条件，在同一回归集上比较失败类别。通过逐项回退或只替换一个段落定位原因，检查修复一种错误时是否损伤其他任务。

### 12. 大模型的解码/采样策略有哪些？

**面试回答示例：** 解码策略控制模型如何从候选 token 中选择输出。贪心直接选最高概率项，beam search 保留多个候选序列；温度调整概率分布，top-k 限制候选数量，top-p 按累计概率截取候选集合。它们会影响多样性和稳定性，但不能保证事实正确。业务问答和工具参数生成通常更重视稳定，创意任务可以允许更多变化。实际选择要在固定任务上评测，同时注意具体模型接口支持的参数可能不同。

**核心回答：** 常见解码包括贪心、beam search、temperature、top-k 和 top-p；策略影响多样性、稳定性与计算量。

**展开要点：** 贪心每步选择最高概率 token；beam search 保留多个候选序列；temperature 改变分布尖锐程度，top-k 保留固定数量候选，top-p 保留累计概率达到阈值的集合。这些参数影响输出多样性，但不能替代正确性校验。不同模型暴露的参数可能不同，应固定配置进行任务评测。

**常见追问：** 工具选择与创意写作如何设置不同策略？

**追问参考回答：** 工具调用通常先试较低随机性，并配合 Schema 和业务校验；创意写作可以适度提高多样性。没有通用最优数值，依据各任务的正确率、重复度和可读性调整。

### 13. 什么是CoT?优缺点是什么？

**面试回答示例：** CoT 是通过中间推理步骤处理需要多步判断的问题，例如先整理条件，再计算结果。它可能改善复杂任务的表现，但会增加生成耗时和成本，而且中间解释也可能包含错误，不能直接当成可靠证据。工程上我更关注可核验的计划、计算结果和最终结论，而不是要求展示所有内部思考。涉及数字或业务规则时，会让工具执行计算，并用测试或原始材料校验，再判断是否需要增加推理步骤。

**核心回答：** CoT 指通过中间推理步骤处理多步问题，可能改善复杂任务，但增加成本且中间文字不保证正确。

**展开要点：** 多步任务可以拆成可检查的中间产物，例如先提取订单字段，再按规则计算资格，最后生成解释。真正有价值的是中间结果能被验证，而不是生成一段看似完整的推理文字。对算术、代码和数据库任务，优先调用计算器、测试或查询工具，并用最终任务结果判断效果。

**常见追问：** 为什么看似合理的步骤仍能得到错误结果？

**追问参考回答：** 中间步骤可能使用错误事实、隐含不成立的假设，或在后续计算中出错；语言流畅也不代表逻辑有效。需要逐项核验关键前提，并用工具或独立测试检查结果。

### 14. 大模型为什么会产生幻觉？怎么系统性治理？

**面试回答示例：** 大模型会产生幻觉，首先因为训练学习的是文本概率，流畅表达并不等于事实正确；其次是知识缺失或过期、检索和上下文不完整、推理出错，以及不确定时仍倾向回答。治理要覆盖整个链路：用可信数据源补证据，让结论绑定引用，用工具和业务代码校验计算及状态，证据不足时澄清或拒答。最后用可答、不可答和冲突样本持续评测。RAG、低温和自检只能降低风险，不能保证完全消除幻觉。

**核心回答：** 大模型幻觉是指生成看似合理、却与事实或已有证据不一致、或缺乏支持的内容。原因包括训练目标并不直接保证事实正确、知识缺失或过期、上下文与检索失误、推理错误，以及不确定时仍倾向给出答案。治理需要把可靠证据、受约束生成、工具与业务校验、拒答机制和持续评测结合起来，不能只靠一句“不要编造”。

**展开要点：**

**一、为什么会产生幻觉？**

1. **训练目标与事实正确性存在差距。** 常见自回归预训练学习的是“给定上下文，下一个 token 的概率”，不是逐条查询事实库并验证真假。模型从语料中学到语言模式和知识，但一句话概率高、表达流畅，不等于事实正确。遇到“请给出某论文及作者”这类常见表达时，它可能按熟悉模式生成一个实际不存在的引用。
2. **训练数据和参数知识有边界。** 语料可能包含错误、冲突和偏见，也可能缺少专业领域、长尾实体或最新信息。知识被编码进参数，不能保证每次准确提取，容易混淆相似人名、产品、年份和规则。私有订单、实时库存等数据若未提供，模型无法凭参数知道当前真实状态。
3. **上下文和检索提供了错误或不完整证据。** 用户问题含糊、长上下文被截断、摘要漏掉限定条件，都会使输入信息不足。RAG 也可能漏召回、命中过期政策，或把其他产品的条款作为证据；即使检索正确，模型仍可能忽略例外、误读表格或把“部分情况”概括为“全部情况”。
4. **模型没有可靠表达知识边界，可能倾向回答或迎合。** 部分训练数据与评价方式偏好完整、自信的答复，却没有充分奖励恰当的澄清和拒答。用户问题中的错误前提也可能被模型沿用。语言上的自信不是可信置信度，模型说“我很确定”不能作为事实验证。
5. **推理、计算和生成过程可能出错。** 模型可能使用错误前提、算错数字、混淆因果关系，前一步错误还会进入后续上下文并被继续展开。较高随机性可能增加不可靠表达，但低温或贪心也可能稳定地产生同一个错误，因此幻觉并不只是采样随机性造成的。

**二、如何系统性治理？**

| 对应问题 | 治理措施 | 需要检查的边界 |
|---|---|---|
| 知识缺失、过期或私有事实不可知 | 用可信且有版本的 RAG、搜索、数据库或业务 API 提供事实 | 检查来源、有效时间和访问权限；检索相关不等于证据充分 |
| 漏检索、证据冲突、上下文丢失 | 优化解析、切分、混合检索与重排，保留来源和关键限定条件 | 不盲目增加 top_k；过多噪声可能干扰答案，冲突信息需明确处理 |
| 模型在证据外自行补全 | 要求先提取证据再回答，区分事实与推断，关键结论绑定来源 | 不能只检查有无引用，还要检查引用是否支持该结论 |
| 数字、规则和实时状态错误 | 让计算器、SQL、测试和确定性业务代码处理计算及规则，模型负责解释 | Schema 合法不代表值正确；还需校验实体、单位、状态和业务口径 |
| 信息不足时强行作答 | 允许“不知道”，缺字段时澄清，证据不足时拒答或转人工 | 不依赖模型自报置信度；依据证据覆盖、冲突和业务校验决定是否回答 |
| 错误被带入实际操作 | 执行前再次验证权限、参数和状态，高风险操作绑定具体审批 | 文本宣称成功不等于执行成功；只有工具回执和真实状态能证明完成 |

**三、形成可验证的治理闭环。**

- **生成前：** 确认问题和必要字段，准备有效证据；数据缺失时先补查或澄清。Prompt 明确证据范围、禁止编造来源并允许拒答，但权限与业务规则落实在程序中。
- **生成后：** 将答案拆成关键事实主张，检查实体、数字、日期和引用支持。可用独立模型辅助核查，但同类模型可能犯相同错误，因此关键结论仍优先用原始证据、确定性规则或人工复核。
- **持续评测：** 建立可答、不可答、过期、冲突、错误前提和计算题样本。分别统计事实正确性、无证据主张比例、引用支持率和拒答表现，同时检查系统是否靠过度拒答“降低幻觉”。记录检索结果、实际上下文、模型及 Prompt 版本，区分检索失败与生成失败。
- **按证据决定是否训练：** 若模型长期误解领域术语或不会恰当拒答，可用高质量监督或偏好数据改善行为；实时事实仍通过外部数据源获取。微调、RAG、反思和低温采样都需要评测，不能承诺完全消除幻觉。

**Agent 场景举例：** 客户问“我的订单能否退款、多久到账”，先查询真实订单、有效退款政策及支付渠道。退款资格和金额由业务代码计算，到账时效引用渠道说明；查询失败或政策未覆盖时明确说明待确认。发起退款后只根据工具回执和账本状态报告进展，不能因模型写了“退款成功”就认定已经完成。

**面试口述建议：** 先讲“概率生成不直接保证事实正确”，再补充知识、上下文、行为与推理四类原因；治理按“补证据、约束回答、工具校验、不足时拒答、评测闭环”展开，并用订单退款举例。

**常见追问：** 如何区分事实错误与未支持主张？用了 RAG 为什么仍会幻觉？temperature 设为 0 能解决吗？模型自检是否足够？幻觉能否完全消除？

**追问参考回答：**

- **如何区分事实错误与不可验证的表达？** 与可信来源或实际状态矛盾的是事实错误；没有证据覆盖其范围的是未支持主张。例如只查看部分订单，就说“全部订单都已退款”。应补查、收窄结论或明确尚未验证。
- **用了 RAG，为什么还会幻觉？** 检索可能漏掉正确证据、命中过期内容；模型也可能误读证据或补出证据没有的结论。因此要分别检查证据是否正确、是否完整，以及答案是否受证据支持。
- **temperature 设为 0 能解决吗？** 不能。它主要减少采样变化，模型仍可能稳定输出最高概率的错误内容；低温不能修复知识缺失、错误检索或推理失败。
- **让模型自检一遍是否足够？** 不足。同一模型可能沿用原来的错误假设，自检只能作为辅助；应引入新证据、工具计算、测试或独立核验。
- **幻觉能否完全消除？** 开放式生成系统不能据此保证。工程上要将目标定义为降低可测错误率，并限制错误影响；确定性业务规则交给程序，证据不足则不做确定承诺。

## 工具调用、接口与协议（第 15—22 题）

### 15. 什么是Function Calling？原理？

**面试回答示例：** Function Calling 让模型把调用意图表达为工具名称和结构化参数，例如输出查询订单工具及订单号。应用先向模型提供工具描述和参数规则，再解析调用请求，完成类型、权限和业务校验后执行，最后把真实结果回传给模型。模型负责建议调用，应用掌握执行权限。实现时还要处理调用标识、多个工具、异常和超时，涉及副作用时加入幂等机制，不能把模型生成的调用文本当成执行成功。

**核心回答：** Function Calling 让模型输出工具名称和结构化参数，应用负责校验、授权、执行及回传结果。

**展开要点：** 调用时应用提供工具名称、描述和参数 Schema，模型返回工具请求及调用标识，应用检查后执行，再将结果回传模型。工具调用是一种结构化决策接口，模型本身并没有获得数据库或操作系统权限。一次响应可能提出多个调用，需要保留每个调用 ID，并明确哪些能并行、哪些有依赖。

**常见追问：** 如何支持多个工具调用及不被允许的工具？

**追问参考回答：** 逐个校验调用并按 ID 回传结果；互不依赖的读操作可并行，依赖或写操作按规则执行。没有授权的工具即使被模型请求也应拒绝，返回可处理的错误，不临时开放权限。

### 16. 如何设计工具名称、描述、参数和返回值？

**面试回答示例：** 设计工具时，我会让每个工具承担清晰的业务职责，名称能够体现动作，描述说明适用场景、限制和副作用。参数尽量采用明确类型、枚举和必要字段，避免让模型填含义模糊的字符串。返回值包含业务状态、结果数据和可处理的错误信息，例如区分订单不存在与查询服务暂时不可用。对于写操作，还要说明确认和幂等要求。最后通过相似工具选择测试，检查模型能否正确区分能力边界。

**核心回答：** 工具要有单一、清晰的业务职责，并让模型知道何时使用、输入限制和结果含义。

**展开要点：** 工具设计要围绕清晰业务动作，例如 query_order 和 propose_refund，比 execute_anything 更容易选择和校验。参数明确单位、枚举、必填项与默认值；返回结果包含状态、数据、来源和可诊断错误。明确只读或有副作用、是否幂等及调用限制，避免模型因为描述模糊而选错工具。

**常见追问：** 把二十个 API 合并成万能工具有什么风险？

**追问参考回答：** 万能工具把权限和参数分支集中到一个入口，增加错误选择、越权和测试复杂度。可以按业务能力聚合少量相关操作，但仍需清楚的动作枚举及每个动作独立校验。

**验证方式：** 用易混淆任务测工具选择率和参数有效率。

### 17. 参数符合 JSON Schema，但业务上无效怎么办？

**面试回答示例：** JSON Schema 只能保证参数结构和基本类型，不能保证业务有效。例如订单号是合法字符串，但订单可能属于其他用户，或者当前状态不能退款。因此执行侧还要验证身份、访问权限、数值范围和业务状态，并尽量在实际提交时再次检查，防止状态变化。失败后返回明确、可操作且不过度泄露信息的错误，让模型补问或调整参数。涉及资金等操作时，不能依赖模型自行判断合法性。

**核心回答：** 类型校验后还需做身份、权限、范围及业务状态校验，返回可操作但不泄露敏感信息的错误。

**展开要点：** JSON Schema 只能验证类型、格式和部分取值范围，无法判断订单归属、当前状态、库存或退款金额是否符合政策。服务端应按认证身份加载资源，再检查业务规则和状态版本；校验通过后才能执行。金额用明确单位，关键写操作应在事务或受约束的更新条件中再次核验，防止校验后状态改变。

**常见追问：** 如何避免错误消息暴露他人的订单是否存在？

**追问参考回答：** 先做权限范围过滤，对不存在或不可访问的资源返回一致的对外错误；详细原因仅进入受控日志。不要把“存在但属于其他用户”的信息直接反馈给模型或客户端。

**验证方式：** 测试越权 ID、过期版本、负金额和超额度。

### 18. LangChain 的输出解析不稳定（JSON经常解析失败），怎么办？

**面试回答示例：** 对于 JSON 解析不稳定，我会先减少输出歧义，优先使用接口支持的结构化输出或工具参数约束，并简化 Schema。应用层仍需解析和验证必填字段、类型及业务含义，不能因为能解析就直接使用。失败时根据错误反馈做有限次数修复，超出次数则明确返回失败。也要检查流式输出是否收齐、是否混入说明文字，以及截断问题。我会统计各类失败比例，避免仅靠正则修补掩盖根因。

**核心回答：** 优先用受支持的结构化输出或工具 Schema，并在应用层执行类型与业务校验。

**展开要点：** 优先使用模型支持的结构化输出或工具参数接口，再通过解析器验证类型、必填字段和枚举。解析失败可做有上限的修复请求，将具体校验错误作为反馈；修复过程中不得执行业务操作。格式正确后仍需业务校验，模型生成的默认值不能自动替代缺失的关键身份、金额或审批字段。

**常见追问：** 字段缺失与字段值越权分别怎么处理？

**追问参考回答：** 字段缺失属于格式或信息问题，可要求补充、澄清或重新生成；越权值属于权限问题，应拒绝执行并记录。不能通过自动“修正”越权值绕过授权检查。

### 19. 什么是MCP？和Function Calling什么关系？

**面试回答示例：** MCP 和 Function Calling 处在不同层次。Function Calling 约束模型怎样表达工具请求，MCP 则标准化客户端怎样发现和接入服务端的工具、资源等能力。例如应用可以从 MCP 服务获取工具定义，再提供给模型；模型提出调用后，由客户端连接服务端执行并回传结果。二者可以配合，但协议接入不等于自动获得权限。实际还要管理身份认证、授权、超时、数据范围和审计记录。

**核心回答：** MCP 标准化客户端与服务端之间的工具、资源和提示等接入；Function Calling 约束模型表达调用请求。

**展开要点：** MCP 为应用与外部能力提供统一的发现和交互方式，Function Calling 则是模型表达调用意图的接口。应用可把 MCP 暴露的工具映射成模型可选工具，但仍负责身份、超时、授权及结果处理。接入时确认协议版本和服务能力，避免把“能发现工具”误认为“调用已经安全可靠”。

**常见追问：** MCP Server 返回超大数据或断连怎么办？

**追问参考回答：** 超大数据应分页、过滤或返回可继续读取的引用；断连后按操作类型判断是否可重试。读请求通常较易恢复，写请求先查执行状态或使用幂等键，不能因连接中断就假定未执行。

### 20. Function Calling、Skill、MCP 三者有什么区别？怎么选？

**面试回答示例：** 我会把三者理解为调用表达、能力接入和流程复用。Function Calling 让模型生成结构化工具请求；MCP 统一外部工具或资源的连接方式；Skill 则封装某类任务的步骤、知识和可选脚本。例如报告 Skill 可以指导分析流程，通过 MCP 获取数据，再由模型发起工具调用。选择取决于问题所在层次，三者可以组合。无论采用哪种形式，执行权限和业务校验都要由应用控制。

**核心回答：** Function Calling 描述模型调用请求，MCP 标准化外部能力接入，Skill 封装可复用流程与知识，三者可以组合。

**展开要点：** Function Calling 解决如何让模型提出结构化动作，MCP 解决不同服务的能力接入，Skill 则封装完成某类任务的操作说明和可选资源。三者可以组合，例如 Skill 指导报告步骤，模型通过 Function Calling 选择工具，应用再通过 MCP 访问资料。是否采用取决于复用范围和维护成本。

**常见追问：** 只有两个内部 API，是否需要 MCP 和 Skill？

**追问参考回答：** 两个稳定内部 API 可以先用直接适配和工具 Schema。需要跨客户端共享工具时再考虑 MCP，需要复用一套任务方法和资源时再考虑 Skill，不必为小系统同时引入所有机制。

### 21. SSE和WebSocket区别？为什么LLM用SSE？

**面试回答示例：** SSE 是基于 HTTP 的服务端单向事件流，适合客户端发起一次请求后持续接收生成内容；WebSocket 则支持双方持续发送消息，更适合频繁双向交互。文本生成通常主要由服务端连续返回片段，因此 SSE 的连接模式比较贴合需求。实时语音或需要持续上传事件时，可以考虑 WebSocket。实际设计还要处理断连、取消、代理缓冲和事件顺序，流式返回也不代表每个片段都是完整业务结果。

**核心回答：** SSE 是 HTTP 上的服务端向客户端事件流，WebSocket 提供双向消息通道；选择取决于交互需求。

**展开要点：** SSE 常用于服务器持续向客户端发送生成片段和任务事件；WebSocket 适合需要持续双向交换的交互。流式输出应携带事件类型、序号和任务 ID，区分文本增量、工具状态、结束及错误。网络重连可能导致事件重复或缺失，因此展示层需要去重或查询最终任务状态。

**常见追问：** 浏览器关闭后后台任务应继续还是取消？

**追问参考回答：** 根据任务语义决定。交互式短请求可随连接关闭取消；已持久化的长任务可以继续，用户凭任务 ID 查询结果。客户端断开与业务取消应作为两个独立事件处理。

### 22. 什么是LLM网关？解决什么？

**面试回答示例：** LLM 网关是业务与多个模型服务之间的统一接入层，可以集中处理鉴权、限流、模型路由、用量统计和调用观测。例如不同任务选择不同模型，业务侧使用相对统一的接口。设计时需要保留供应商能力差异，不能只做接口字段转换。发生错误时，应区分重试、降级和切换模型的适用条件，流式请求也要考虑已输出内容。涉及敏感数据时，还需要明确日志脱敏和允许访问的模型范围。

**核心回答：** LLM 网关集中做模型访问、路由、鉴权、限流、用量和观测，减少各业务重复接入。

**展开要点：** 网关统一封装认证、模型路由、限流、配额、超时、使用量记录和错误转换，减轻业务服务直接适配多个供应商的成本。路由要考虑工具协议、输出 Schema、上下文长度和任务质量，而非只按价格。为每次请求记录实际模型和配置，避免故障切换后无法解释行为变化。

**常见追问：** 什么情况下不能自动换模型重试？

**追问参考回答：** 涉及未确认的外部副作用、另一模型不支持所需协议、上下文无法容纳，或质量与数据处理要求不满足时不能盲目切换。需先确认执行状态，并通过预先验证的降级策略处理。

## 记忆与上下文管理（第 23—27 题）

### 23. 记忆怎么设计？

**面试回答示例：** 记忆设计首先要区分工作上下文、会话状态、执行快照和跨会话长期记忆。工作上下文服务当前生成，任务状态记录进展，快照用于恢复，长期记忆保存经过确认的偏好或事实。我会分别定义写入条件、有效期和删除方式，避免把模型推测永久存下来。读取时按用户与租户过滤，并根据任务选择相关信息。长期记忆应带来源和时间，冲突时更新或澄清，而不是把全部历史消息塞进上下文。

**核心回答：** 分清工作上下文、会话状态、执行 Checkpoint 和跨会话长期记忆，分别定义生命周期。

**展开要点：** 可把记忆分为当前上下文、任务状态和长期可复用信息。长期记忆记录来源、主体、时间、置信度及适用范围，避免把模型推测存成事实。读取时按用户或租户过滤，再检查相关性与有效期。偏好、政策、订单状态的生命周期不同，不应全部永久保存，也不应把 Checkpoint 当成长期知识库。

**常见追问：** 用户纠正旧事实或要求删除记忆怎么办？

**追问参考回答：** 记录纠正版本并使旧事实失效，避免只新增一条矛盾记忆；删除时同时处理主存储、检索索引及缓存，并按既定留存规则处理日志。后续检索应验证已删除信息不再可用。

### 24. Agent的记忆压缩？

**面试回答示例：** 记忆压缩的目标是在有限上下文中保留继续任务所需的信息。我会优先保存目标、约束、已确认事实、关键决策、待办和产物引用，把完整原文留在外部存储。摘要需要保留金额、日期、否定条件等容易丢失的细节，并区分事实与推断。复杂任务可以分阶段压缩，后续按需找回原文。验证时让系统从压缩状态继续执行，检查是否遗漏限制，而不只比较摘要看起来是否通顺。

**核心回答：** 上下文压缩需要保留目标、约束、关键事实、待办、决策和产物引用，把可恢复原文存到外部。

**展开要点：** 压缩时保留目标、约束、已确认事实、未解决问题和关键工具结果，将重复对话变成摘要。数字、身份、审批参数和来源标识尽量结构化保存，原始记录仍可检索。摘要带版本及来源范围；压缩后用关键字段一致性检查防止漏掉限制，也避免将“模型曾猜测”变成“已经确认”。

**常见追问：** 摘要错误后如何追溯和修复？

**追问参考回答：** 保存摘要所引用的原始消息或证据 ID，定位错误后重新生成受影响摘要，并使相关缓存失效。恢复时从可信状态补齐关键字段，不仅在错误摘要上追加一句纠正。

### 25. 如何分配历史消息、检索证据和工具结果的 Token 预算？

**面试回答示例：** 分配 Token 预算时，我会先预留输出空间，再确保系统指令、任务目标和必要状态能够完整进入上下文。历史消息只保留与当前任务有关的内容，检索证据按相关性和覆盖范围选取，工具结果则优先过滤、聚合或摘要。不同任务的比例应动态调整，例如跨文档问答更重视证据，恢复执行更重视状态。截断前要保留关键限定条件，并记录实际输入，便于解释答案为什么出错。

**核心回答：** 先预留输出空间，再按任务保留指令、目标、必要状态和高价值证据，其他信息按需获取。

**展开要点：** 先为可信指令和工具定义预留空间，再为当前问题、关键状态、检索证据和必要历史分配预算，同时预留输出及后续工具观察。裁剪优先删除重复和低相关信息，保留最新约束、审批对象与来源。使用与模型匹配的 tokenizer 估算，不能只按字符数；必要时降采样、摘要或追加检索。

**常见追问：** 删除旧工具消息会不会使模型协议失效？

**追问参考回答：** 可能。某些消息协议要求工具请求与结果配对；裁剪时应保留完整调用组，或转换成合法的摘要消息，同时保存原始结果引用。不能随意删除一半调用记录。

**验证方式：** 比较压缩前后关键事实、任务成功率与输入 Token。

### 26. MCP查询出来的数据有十几万tokens数量级，模型怎么处理？

**面试回答示例：** 十几万 Token 的工具结果不适合直接交给模型。我会让数据留在外部，通过过滤、分页、聚合和受限查询返回任务需要的部分。例如分析订单时，先用程序统计整体指标，再读取异常记录，而不是让模型逐行计算。模型获得结果摘要、字段说明和数据引用，必要时继续查询。这样既控制上下文与费用，也保留完整数据。需要注意抽样只能支持相应范围的结论，不能把局部结果描述成全量事实。

**核心回答：** 超大工具结果应留在外部产物中，通过分页、过滤、聚合和摘要提供受限视图，避免全量塞入模型。

**展开要点：** 先在数据库或工具端按问题筛选、聚合，再返回模型真正需要的字段和统计结果。对大列表提供总量、分页游标、排序条件和小样本，让模型能继续查细节。计算交给确定性程序，模型负责理解和解释；仅把十几万 token 文本做一次摘要，容易遗漏异常记录和精确数字。

**常见追问：** 模型如何发现摘要没有覆盖的问题？

**追问参考回答：** 返回覆盖范围、筛选条件、未读取数量和聚合口径，模型据此知道证据边界。对异常、缺失或需要逐条核查的问题触发补查；摘要自身不能证明被省略部分没有问题。

### 27. 工具返回超大结果时，如何保留可追溯性？

**面试回答示例：** 保留大结果的可追溯性，我会保存完整产物，并返回产物标识、查询条件、字段结构、行数和版本等元数据。模型看到的摘要或片段必须能够定位到原始记录，后续通过分页或过滤继续读取。访问链接也要继承用户和租户权限，避免共享产物造成数据泄露。生成结论时引用具体来源与范围，审计时可以还原当时使用的证据。这样即使上下文只包含少量数据，也能核查结果是否成立。

**核心回答：** 全量结果存到受权限控制的产物存储，返回 ID、查询条件、Schema、行数和受限视图。

**展开要点：** 工具可返回 result_id、数据版本、总数、筛选条件、字段描述、摘要与局部样本，完整结果放在受控存储中按需读取。引用同时记录行标识或页码等位置，防止后续数据更新导致无法复核。对数值结论记录计算过程与输入快照，使用户能区分完整统计、抽样观察和模型概括。

**常见追问：** 没有读完整数据能否声称“所有记录均满足”？

**追问参考回答：** 只有确定性查询或检查确实覆盖完整目标集合，且明确统计口径时才可作全量结论。仅阅读样本或摘要，应说明范围，不能推断所有记录都满足条件。

**验证方式：** 验证答案涉及的记录可从原始产物复核。

## RAG、知识更新与结构化检索（第 28—49 题）

### 28. 什么是RAG它的完整工作流程是什么？

**面试回答示例：** RAG 的流程分成离线建库和在线问答。离线先解析文档、清洗内容、切分片段，再生成向量并保存来源、版本和权限等元数据。在线把用户问题转换成检索请求，召回候选片段并重排，组织证据后让模型回答并给出引用。我会分别检查检索是否找到正确材料，以及答案是否受材料支持。证据不足时需要澄清或拒答，因为检索到相关文本并不保证答案正确。

**核心回答：** RAG 分为离线摄取建索引与在线检索生成：解析、切分、索引，然后检索、重排、组织证据并回答。

**展开要点：** 离线阶段解析文档、清洗内容、切分片段、生成向量并建立带元数据的索引；在线阶段理解问题、检索候选、重排、组装上下文，再生成带引用的回答。每个片段应保留文档 ID、版本、位置和权限。评测需要拆分检索是否找到证据、证据是否足够以及生成是否忠实，避免把所有失败都归因于模型。

**常见追问：** 检索不到答案时如何处理？

**追问参考回答：** 先区分知识库缺失、查询表达不匹配和权限限制；可以改写查询或补充检索，但仍无证据时应澄清、拒答或转人工。不要以模型记忆填补需要准确来源的业务事实。

### 29. RAG解决了哪些问题？

**面试回答示例：** RAG 主要解决模型参数知识难更新、私有资料不可直接获取和回答缺少来源的问题。通过在生成时提供外部证据，系统可以使用最新政策或企业文档，并保留引用，减少依赖模型记忆。例如政策调整后可以更新索引，而不必立即重新训练模型。它的效果依赖解析、检索和证据使用质量，也会受旧资料、漏召回和误读影响。因此需要版本管理、权限过滤和答案核验，不能把接入知识库等同于消除幻觉。

**核心回答：** RAG 让模型在回答时使用外部、可更新且可引用的知识，减少依赖参数记忆。

**展开要点：** RAG 主要提供可更新、可追溯且按权限访问的外部信息，适合企业政策、产品资料和实时业务数据。它能减少依赖模型参数记忆，但效果仍受解析、索引、检索及生成影响；找到一段相关文字也不代表足以回答问题。涉及数字计算或实时状态时，往往还需数据库和业务工具。

**常见追问：** 什么时候长上下文直接读文档更合适？

**追问参考回答：** 文档数量少、总长度能放入上下文，且问题需要整体分析时，可以直接读全文作为基线。若数据量大、频繁更新、访问权限复杂或只需局部证据，检索通常更合适。

### 30. RAG和微调怎么去选择？

**面试回答示例：** 我会先判断需求属于知识更新还是行为调整。需要查询最新政策、私有资料并提供引用时，优先考虑 RAG；需要稳定输出格式、理解领域表达或改善特定任务行为时，再评估微调。例如客服可以用 RAG 获取当前政策，通过训练改善分类或拒答行为，两者并不冲突。实际应先建立 Prompt 和检索基线，再比较效果与维护成本。动态事实仍要从可靠数据源获取，不能只靠微调记住所有业务信息。

**核心回答：** RAG 主要解决知识获取和更新，微调主要改变行为、表达或任务能力，两者可以组合。

**展开要点：** RAG 将变化事实放在外部知识源；微调则通过训练改变模型的任务行为、表达方式或特定能力。企业知识经常更新时优先检索，需要稳定格式、领域分类或工具使用习惯时可考虑微调。两者可结合，但要先证明瓶颈所在，不能因为检索效果差就直接训练模型来记住全部文档。

**常见追问：** 领域术语理解差与事实知识缺失如何区分？

**追问参考回答：** 给模型正确证据后仍误解术语或规则，可能是任务理解问题；补充证据后即可回答，则主要是知识供给问题。用这两类样本分别验证 Prompt、检索和微调收益。

### 31. 文档切割有哪几种策略？为什么要overlap?

**面试回答示例：** 文档切分可以按固定长度、句段、标题结构、语义或父子层级进行。我会根据文档类型选择策略：说明书保留章节路径，表格保留表头与行列关系，长段落再按长度细分。Overlap 用于缓解证据落在边界两侧的问题，但过大也会增加重复检索和存储。切分尺寸需要结合真实问题评测，检查一块是否足够支持答案，以及检索后是否需要补充父块或邻近片段。

**核心回答：** 切分可按固定长度、标题结构、句段、语义或层级进行；overlap 缓解边界处证据被拆开的问题。

**展开要点：** 固定长度切分容易实现，按句子、段落、标题或语义边界切分更有利于保持完整论述。overlap 用来减少边界附近信息丢失，但会增加索引量和重复证据。每个片段可带标题路径、文档版本及所属章节，检索命中后读取相邻片段或父段落；表格、代码和条款最好使用专门结构处理。

**常见追问：** chunk 大小如何实验确定？

**追问参考回答：** 固定模型与任务集，比较不同片段长度及重叠比例的证据召回率、答案质量、延迟和成本。按短事实、跨段推理等问题分层评估，而不是只选一个平均分最高的配置。

### 32. 在进行切割时，如何避免语义被切割掉？

**面试回答示例：** 避免语义被切断，我会先尊重句子、段落和章节边界，并把标题路径、定义及限定条件保留在片段中。表格要让数据与表头对应，列表也要保留共同的前提。对于很长的章节，可以用小块检索，再返回父块或相邻证据，兼顾召回和理解。不能只靠增加重叠解决所有问题，还需要检查否定条件、例外和跨段引用是否完整。最后用实际问答样本验证切分后的证据能否独立支撑结论。

**核心回答：** 优先保留完整句段、标题路径和表格关系，可采用子块检索后补充父块或邻近证据。

**展开要点：** 优先使用标题树、段落和句子边界，保持定义、例外条款和结论相邻；长度超限时再递归切分。索引可以使用小片段提高命中率，返回时扩展到父段落增加理解上下文。对跨页表格或编号条款保留连续关系，不能把正文中的“上述条件”与对应条件完全分离。

**常见追问：** 跨章节问题如何检索？

**追问参考回答：** 先识别子问题并检索各章节证据，再按文档结构扩展相邻内容或父章节。需要全局比较时可建立章节摘要索引，但最终结论仍回查原文，避免只依赖摘要。

### 33. Embedding怎么选？怎么评估？

**面试回答示例：** Embedding 选型我会建立包含真实问题和相关文档的领域数据集，比较召回率、排序表现、语言覆盖、延迟和成本。向量维度高或通用榜单好，不一定适合企业术语和编号查询。测试时保持切分、索引参数和候选数量一致，必要时加入关键词检索作为对照。还要考虑查询与文档的编码方式是否匹配，以及更新模型后是否需要重新建索引。最终看业务问题能否找到正确证据。

**核心回答：** 用领域任务比较 Embedding 的检索效果、语言覆盖、向量维度、延迟和成本。

**展开要点：** 评估 Embedding 要使用真实的中英文、专业术语和长短查询，检查正确证据是否进入候选集合。关注 Recall@k、MRR、向量维度、吞吐、模型部署成本及支持长度。更换模型会改变向量空间，一般需要重建文档向量，并保持查询与文档编码方式匹配。通用相似度表现不能替代业务检索评测。

**常见追问：** 测试集如何避免文档或问题泄漏？

**追问参考回答：** 按文档来源、时间或主题划分数据，避免同一文档的相似问题同时用于调参和测试。测试问题及标准证据不进入合成扩充或训练流程，保留独立最终测试集。

### 34. 向量数据库该怎么选？

**面试回答示例：** 向量数据库选型需要结合数据规模、访问模式和运维能力。我会重点测试带租户及权限过滤时的召回、延迟、增量更新和删除效果，并评估持久化、备份和可用性。已有数据库能满足需求时，可以先减少额外系统；规模或检索需求更复杂时再考虑专门方案。测试负载应接近真实场景，不能只看无过滤条件的性能。还要明确索引更新和数据版本的一致性，避免检索到已失效内容。

**核心回答：** 向量库选型看数据规模、过滤能力、更新模式、可用性、运维和与现有数据库的集成。

**展开要点：** 先看数据规模、更新频率、过滤条件、混合检索能力和运维环境，再选向量存储。测试近似索引参数对召回、内存及延迟的影响，并覆盖删除、增量更新、备份恢复和并发检索。小规模系统可以使用现有数据库的向量能力，数据量大且性能要求高时再评估专门服务。

**常见追问：** 向量检索与元数据过滤的执行顺序有什么影响？

**追问参考回答：** 先过滤可能减少候选范围但影响索引路径；先做向量搜索再过滤可能候选不足，并触及不该暴露的数据。需要在检索访问边界强制权限，测试高选择性过滤下的召回和延迟。

### 35. 向量检索和关键词检索的区别？为什么需要混合检索？

**面试回答示例：** 关键词检索擅长精确匹配编号、名称和专业术语，向量检索擅长处理同义表达与语义接近的问题。例如用户问某个错误码，关键词通常更直接；用户用口语描述故障，向量可能更容易召回。混合检索可以同时获得两类候选，再去重、融合排序和重排。不同分数不能随意直接相加，需要合适的融合方式。最后按查询类型比较效果，并在召回阶段执行权限过滤。

**核心回答：** 关键词检索擅长精确名称、编号和术语；向量检索擅长语义近似，混合检索利用二者互补。

**展开要点：** 关键词检索善于匹配型号、姓名、编号和专业术语，向量检索善于处理同义表达和语义相关性。混合检索分别召回再融合，可用排名融合减少不同分数尺度的影响，再通过重排排序。关键标识可做精确查询，避免“语义相似”把不同订单或产品混为一谈。

**常见追问：** 为什么混合检索仍可能漏召回？

**追问参考回答：** 原始内容缺失、切分破坏证据、错误权限过滤或查询意图不清都可能漏召回。两种检索都没找到正确候选时，融合算法也无法凭空补出证据。

### 36. 什么是查询重写？

**面试回答示例：** 查询重写是把用户表达转换成更适合检索的问题，例如结合历史消息补全指代、提取术语或把复杂问题拆成多个子问题。关键是保留原始意图和限制，不能把模型猜测写成用户已确认的条件。我会同时保留原问题，并在必要时多路检索后合并候选。对于含订单号、时间范围等精确字段的问题，要确保重写不会改错。效果通过召回改善和意图偏移比例验证，而不是只看改写文本是否更流畅。

**核心回答：** 查询重写将用户表达转换为更适合检索的问题，例如补全指代、提取关键词或拆分子问题。

**展开要点：** 查询重写可将“那个怎么退”补全为当前订单的退款政策问题，或把复杂问题拆成多个检索子问题。重写时保留产品、时间、金额、否定和权限等约束；原始查询应作为一条检索路径，防止改写偏离用户意图。记录改写文本和证据变化，避免不可解释地扩大搜索范围。

**常见追问：** 如何评测改写收益与错误？

**追问参考回答：** 比较原始查询与重写查询的正确证据召回、答案质量和约束丢失率。单独检查多轮指代、否定、数字和时间样本；召回增加但意图漂移的改写应判为失败。

### 37. 检索后为什么要重排序？然后Bi Encoder和Cross Encoder的区别？

**面试回答示例：** 检索通常先用 Bi-Encoder 做大规模召回，因为问题和文档可以分别编码，文档向量也能提前计算。Cross-Encoder 则联合处理问题与候选文档，能够更细致地判断相关性，但逐对计算成本较高，所以适合重排少量候选。重排可以改善前几个结果的质量，却无法找回完全没召回的证据。我会分别评测召回覆盖和排序效果，再根据延迟预算选择候选数量，避免只增加模型复杂度。

**核心回答：** Bi-Encoder 分别编码问题和文档，便于预计算与大规模召回；Cross-Encoder 联合处理二者，适合对少量候选重排。

**展开要点：** Bi-Encoder 将查询与文档分别编码，文档表示可预计算，适合大规模召回；Cross-Encoder 联合读取两者并计算相关性，适合对较小候选集精细排序。重排前需要保证正确证据已经被召回，并控制候选数量和输入长度。重排分数通常不是可直接解释的事实置信度。

**常见追问：** 什么时候直接跳过重排？

**追问参考回答：** 精确 ID 查询、候选极少或对照评测显示重排收益不足时可跳过。还应考虑延迟预算；若主要瓶颈在漏召回，先修召回比增加重排更有效。

### 38. 怎么提升RAG的泛化召回能力,让同一段内容多角度被找到？

**面试回答示例：** 让同一内容被不同问法找到，可以为原文建立标题、摘要、关键词和可能问题等辅助表示，也可以结合查询改写与混合检索。例如退款规则除了原文，还可以关联退货条件和到账时间等问题视角。辅助表示只用于提高发现概率，回答仍要回到原始证据，防止生成摘要引入错误。评测要覆盖同义词、口语和专业术语，同时观察错误召回与额外成本，避免扩展越多噪声越大。

**核心回答：** 可增加标题、摘要、关键词、问题视角等辅助表示，同时保留原始证据。

**展开要点：** 可以为片段建立标题、关键词、别名和合成问题等多种检索入口，或针对不同用户表述生成多路查询。多表示都应关联同一原文 ID，检索后合并去重并回到真实内容。合成问题用于提高匹配，不应直接作为事实证据；还需检查生成文本是否引入不存在的条件或结论。

**常见追问：** 如何防止合成问题污染答案？

**追问参考回答：** 把合成内容标记为检索辅助字段，只将原文作为回答证据。校验合成问题与原文的对应关系，并保留来源 ID，禁止把模型生成的答案混入权威知识库。

### 39. 怎么系统性的优化RAG的检索相关性？

**面试回答示例：** 优化检索相关性，我会先建立包含相关证据标注的基线，再把失败分成解析错误、切分不当、语义不匹配、权限过滤和排序问题。针对原因分别调整元数据、切分、混合检索、查询改写或重排，每次尽量只改变一个因素。例如候选里已有正确材料但排位低，应优先处理排序。评测同时看召回、排序、延迟和不同查询类型，防止只提升少数样本，却损害整体表现。

**核心回答：** 先建立检索基线，再针对错误类别优化切分、元数据、混合检索、查询改写和重排。

**展开要点：** 按“查询理解→候选召回→融合重排→上下文组装”逐层优化。先建立有标准证据的小型任务集，检查错例属于术语、切分、过滤还是排序问题。对复杂问题补充子查询，对精确实体增加关键词路径，再测试候选数量和重排；一次只改少数变量，记录质量与成本变化。

**常见追问：** 召回增加但答案变差，如何解释？

**追问参考回答：** 更多候选可能带来无关、过期或相互冲突的内容，也可能挤掉关键证据。应检查去重、版本优先级、重排及上下文裁剪，不只用召回数量判断收益。

### 40. 如何提升检索或生成式搜索的 Top 1 准确率？

**面试回答示例：** 提升 Top 1 前，我会先明确目标是第一条文档正确，还是最终答案正确。然后检查正确证据是否进入候选集合；没有进入就优化解析、索引和召回，已经进入但排位低则优化融合或重排。对于第一条文档无法完整回答的多跳问题，还需要组合证据，不能强求单条覆盖。最后使用固定标注集比较首位命中和答案支持情况，并设定证据不足的处理方式，避免为了命中率输出不可靠答案。

**核心回答：** 提升 Top 1 要拆解为召回覆盖、候选排序和答案验证，并先确定目标是正确文档还是正确答案。

**展开要点：** Top 1 优化需要明确定义首条正确：是包含答案的片段、正确文档，还是正确对象。准备容易混淆的候选和难负样本，优化实体匹配、元数据过滤、重排训练及分数融合。对需要多段证据的任务，同时关注证据集合覆盖率，防止把一个局部正确片段误当作完整答案。

**常见追问：** Top 1 提升会不会牺牲多证据问题？

**追问参考回答：** 可能。单事实任务可以重点看首条命中，多证据任务则需评估 Recall@k、证据覆盖及最终答案。上线策略可以按问题类型保留多个互补候选。

### 41. 什么是生成式排序？如何明确任务并构建训练数据？

**面试回答示例：** 生成式排序这个名称可能指模型直接输出候选文档的顺序，也可能指生成文档标识，因此我会先澄清任务定义。如果是候选排序，输入应包含问题和候选内容，输出可解析的标识序列，并检查是否遗漏、重复或生成不存在的标识。训练数据需要可靠的相关性标注和困难负例，避免把原始展示位置当成正确顺序。评测时比较排序质量、延迟和稳定性，确认它比普通重排方案带来收益。

**核心回答：** 生成式排序可能指模型输出文档次序，也可能指生成文档标识；面试应先澄清定义。

**展开要点：** “生成式排序”可能指模型为候选生成相关性判断，或直接输出候选顺序；若模型生成文档标识来检索，则又是不同任务。先明确输入、输出和候选范围，再构造相关性标签或偏好对。训练与评测要包括难负样本、候选顺序扰动和非法输出检查，不能只观察模型解释是否流畅。

**常见追问：** 相比 Cross-Encoder 有什么收益和代价？

**追问参考回答：** 生成式模型便于表达复杂排序条件和解释，但通常增加 token 成本、延迟及格式校验，还可能有位置偏差。Cross-Encoder 输出分数较直接，适合固定候选排序；选择应依赖任务对照实验。

### 42. 有哪些更复杂的RAG范式？

**面试回答示例：** 更复杂的 RAG 包括多跳检索、层级检索、查询路由、GraphRAG 和 Agentic RAG。它们分别适合跨证据推导、长文档组织、不同数据源选择、实体关系分析和动态补查。例如先查产品关系，再查对应政策，就可能需要多跳。我的原则是先用简单检索建立基线，再针对具体失败增加结构。复杂方案会带来索引、协调和延迟成本，因此需要验证答案质量提升，并保留来源与明确的停止条件。

**核心回答：** 可考虑多跳检索、层级检索、查询路由、GraphRAG 或 Agentic RAG，分别解决不同结构的问题。

**展开要点：** 复杂 RAG 可以引入多跳检索、查询分解、图结构、分层摘要或模型自主选择检索工具。多跳适合证据分散，分层索引适合长文档，图结构适合明确关系。先用普通检索建立基线，再针对特定失败增加机制，并设最大检索轮次和证据检查，避免每个问题都走复杂流程。

**常见追问：** 什么证据证明需要 Agentic RAG？

**追问参考回答：** 若失败主要来自需要根据前一次结果决定下一次查询，且固定检索无法覆盖，可以尝试 Agentic RAG。对照评测需显示新增成功率高于额外成本，并检查循环和错误扩散。

### 43. 知识库如何动态更新？最难的地方在哪？

**面试回答示例：** 知识库动态更新要处理新增、修改和删除，也要保证用户不会同时看到混乱版本。我会给文档和片段设置稳定标识，记录内容版本，变更后增量解析与建索引，再验证并发布。删除必须传播到向量索引、缓存和引用访问层。难点是更新过程的一致性，以及失败时恢复和回滚。例如旧政策替换后，不能只加入新内容而让旧条款继续命中。还要记录生效时间，保证回答采用适用版本。

**核心回答：** 动态更新要支持增量摄取、稳定标识、版本替换、删除传播和可回滚发布。

**展开要点：** 更新链路应跟踪原文件版本和内容变化，只重建受影响片段，并同步处理删除、权限和索引缓存。为一批更新建立完整索引版本，验证后切换读流量；旧版本保留必要恢复能力。难点是避免正文已更新而向量、摘要或缓存仍是旧内容，尤其涉及政策生效时间时必须保留版本语义。

**常见追问：** 用户正在检索时索引更新怎么办？

**追问参考回答：** 让一次请求读取同一索引快照，或明确记录各证据版本。大更新可用新索引构建完成后切换，避免半新半旧；紧急撤销权限则应在读接口即时检查，不能只等待索引更新。

### 44. 如何去量化RAG效果？

**面试回答示例：** RAG 评测要把检索与生成分开。检索侧检查相关证据是否进入候选、排序是否合理，可以用召回率和排序指标；生成侧检查答案正确性、证据支持、引用准确及拒答表现。评测集需要包含可答、不可答、过期资料和冲突问题，并覆盖真实问法。在线还要观察延迟、成本和用户反馈。答案看起来流畅不能证明系统有效，评价时应能定位是没找到材料，还是找到材料后使用错误。

**核心回答：** 检索评测关注相关证据是否被找到和排好，生成评测关注答案正确、证据支持与引用准确。

**展开要点：** 检索指标包括 Recall@k、MRR 和 nDCG，生成指标包括回答正确性、证据支持、引用准确性和拒答表现。建立可答、不可答、冲突、过期及越权问题集，结合人工检查与程序规则。自动评分器也有偏差，关键样本需要校准；最终指标还应包含延迟、成本和用户任务完成情况。

**常见追问：** 如何检测引用正确但结论不被证据支持？

**追问参考回答：** 把答案拆成关键事实主张，逐条检查引用片段是否支持该主张及其范围。引用文件存在只证明链接有效，不能证明结论正确；数字、时间和条件需要专门核验。

### 45. RAG上线效果差，该怎么排查？

**面试回答示例：** RAG 上线效果差时，我会从真实失败问题入手，沿解析、切分、索引、召回、重排、上下文和生成逐层检查。先看原文是否正确入库，再看正确证据是否进入候选，以及是否真正进入模型输入。若证据完整但答案仍错，才重点调整生成约束和核验。也要检查租户过滤、旧版本和线上配置差异。修复后用同一组样本回归，避免一开始就换模型或修改提示，却没有找到原因。

**核心回答：** 沿解析、索引、检索、重排、上下文和生成逐层定位，不应直接改 Prompt 或换模型。

**展开要点：** 先抽取失败请求及对应文档版本，检查解析和索引是否有正确证据，再看召回候选、重排结果、实际送入模型的上下文及最终回答。分别做“人工提供正确证据”和“使用原检索结果”的对照，定位是检索不足还是生成误读。排查时保留原配置，避免同时改模型、切分和 Prompt 后失去归因。

**常见追问：** 给模型正确证据后能否答对，说明什么？

**追问参考回答：** 能答对说明知识供给很可能是主要瓶颈，应检查召回、排序和上下文裁剪；仍答错则需检查任务表述、证据冲突及模型理解。这个实验用于缩小范围，不能单独排除所有交互问题。

### 46. RAG中结构化数据（数据库字段、表格）怎么处理？

**面试回答示例：** 结构化数据需要按问题类型处理。查询某条记录的说明可以结合文本检索，但精确筛选、计数、求和或关联分析应优先用数据库和确定性计算。例如用户问某月销售额，应该执行受限查询再让模型解释结果，而不是检索几个片段后估算。混合问题可以分别查数据库和制度文档。关键是保存字段含义、单位、时间范围及业务口径，并对权限、查询范围和结果进行验证。

**核心回答：** 事实查找可用 RAG，精确筛选和统计更适合结构化查询，混合问题可路由到两种工具。

**展开要点：** 结构化事实优先从数据库或表格查询，非结构化解释由文档检索提供。为字段建立含义、单位、时间范围和权限说明，把数字与业务口径一起返回。比如销售额需要区分已支付、退款后净额及币种；最终答复同时引用数据快照和政策说明，避免模型自行推导隐含口径。

**常见追问：** 财务数字相同但统计口径不同怎么办？

**追问参考回答：** 先核对时间范围、组织范围、币种、是否含税及去重规则，明确各指标定义。数值恰好相同不代表含义一致；必要时分别列出，不能直接合并。

### 47. RAG中在文档中的表格该如何去处理?

**面试回答示例：** 文档表格处理首先要恢复表头、行列关系、合并单元格和上下文说明，再决定存储形式。小表可以转换成带标题的 Markdown，复杂表可用 JSON 或关系结构，精确统计则放入数据库处理。切分时应让每行保留必要表头，避免数值失去含义。还要关注单位、脚注和跨页表格，解析后抽样核对原文。最终根据任务返回相关行或计算结果，并保留能定位原始表格的引用。

**核心回答：** 先识别表格结构和上下文，再选择原始表、Markdown、JSON 或数据库等表示服务不同任务。

**展开要点：** 解析表格时保留表名、列头、合并单元格、单位和脚注，跨页表格需要恢复连续关系。检索可以用表格说明和行级文本，精确数值通过结构化数据读取。大表先按条件过滤，计算交给程序；每行或单元格带来源位置，防止生成时把相邻行列拼接成错误事实。

**常见追问：** OCR 表格识别错位如何检测？

**追问参考回答：** 检查列数、数据类型、合计关系和跨页表头一致性，对关键字段抽样比对原图。低置信度或无法通过规则的表格应标记待复核，不能只依赖 OCR 文本看起来通顺。

### 48. 如何实现Text-to-SQL?

**面试回答示例：** Text-to-SQL 的重点是让问题、数据库结构和业务定义正确对应。我会先定位相关表、字段及关联关系，明确时间和指标口径，再生成 SQL。执行前校验语法、访问权限、允许语句、行数和资源限制，通常采用只读受限环境。结果出来后还要检查空值、重复关联和聚合范围是否合理。问题含糊时先澄清，不能随意猜字段。查询结果与生成过程应记录，方便复现和核查。

**核心回答：** 流程是理解问题、定位 Schema 和业务定义、生成 SQL、校验权限与语法、受限执行并核查结果。

**展开要点：** Text-to-SQL 先检索相关表、字段、关系和少量业务示例，再生成查询。执行前通过 SQL AST 检查语句类型、表列白名单和风险操作，使用只读账户及资源限额；身份过滤由可信服务层或数据库策略落实。结果返回口径、行数和截断信息，复杂查询可先检查执行计划，防止错误 JOIN 放大数据。

**常见追问：** 如何避免查询其他租户或生成高成本 JOIN？

**追问参考回答：** 租户限制由数据库策略或受控查询模板强制执行，不能只提示模型添加 WHERE。限制表关系、执行时长、资源和结果量；LIMIT 限制输出不一定减少扫描，高成本 JOIN 仍需拦截或优化。

### 49. 如何处理百万字 Word 文档并实现检索与综合问答？

**面试回答示例：** 百万字 Word 文档应先离线解析，保留标题层级、段落、表格及来源位置，再建立片段索引和章节摘要。在线针对具体问题检索相关证据，综合分析则拆成多个子问题，逐步收集资料并汇总。例如比较全书多个章节的观点，可以先定位章节，再提取证据，而不是一次塞入全部原文。摘要只能辅助导航，关键结论回查原文，同时控制查询预算、保留引用并检查是否遗漏重要章节。

**核心回答：** 大文档采用离线解析、分层索引和在线检索，复杂综合任务再加入受控 Agent 编排。

**展开要点：** 先解析正文、标题层级、表格、注释及文件版本，再建立片段索引和章节摘要索引。精确问答使用局部证据，综合归纳按章节抽取要点后合并，并回查引用。百万字文档要分批处理和缓存中间产物，避免一次放入上下文；DOCX 页码依赖渲染，定位可先用段落与章节 ID。

**常见追问：** 跨章节归纳与精确查找采用同一方案吗？

**追问参考回答：** 不宜完全相同。精确查找重视命中原文细节，跨章节归纳需要覆盖多个章节并检查遗漏与冲突。可以共享解析与索引基础，但检索范围、合并策略和验收标准应区分。

## 执行可靠性、审批与恢复（第 50—57 题）

### 50. 你的系统里API调用失败怎么办？重试机制是怎么设计的？

**面试回答示例：** API 失败后，我会先区分参数、权限等不可重试错误，以及限流、临时网络故障等可重试错误。可重试场景设置次数和总时间上限，使用退避与随机抖动，并遵守服务端的等待要求。涉及退款等副作用时，超时不能直接理解为没执行，要先用幂等键或状态查询确认结果。最终失败要返回明确状态并保留记录，避免层层重试放大流量。必要时加入熔断或人工处理。

**核心回答：** 先分类错误，再为可重试的临时故障设置有上限的退避重试；副作用操作需确认执行状态。

**展开要点：** 把错误分成临时故障、参数错误、权限错误、业务拒绝和执行状态未知。临时故障设置次数上限、指数退避及随机抖动，避免多个实例同时重试形成压力；单次超时也要服从总任务时限。写接口先记录操作标识并确认是否支持幂等，对未知状态进入查询或对账流程，不让模型凭“失败”文本决定重复执行。

**常见追问：** 请求成功但响应丢失，如何避免重复下单？

**追问参考回答：** 同一订单请求复用稳定幂等键，外部服务保存该键对应的结果；超时后先查询操作状态，必要时使用同一键重试。若对端无幂等和查询能力，应对账或人工确认。

### 51. 如何设计幂等键及其作用范围？

**面试回答示例：** 幂等键用来识别同一业务操作的多次尝试，例如同一笔退款在网络超时后重试。键应包含可信租户、操作类型和稳定业务标识，重试时保持不变，而新业务意图使用新键。服务端需要把键、请求摘要和执行状态持久化，并通过唯一约束处理并发。相同键但参数不同应拒绝或明确报错。还要定义有效期和范围，不能只在内存里缓存一下，也不能让模型每轮重新生成键。

**核心回答：** 幂等键应标识同一业务操作的重复尝试，包含租户、操作类型和稳定业务标识，不能每次重试重新生成。

**展开要点：** 幂等键代表一次业务意图，不只是一次 HTTP 请求。可以采用租户、操作类型和订单操作 ID 的组合，在执行记录中保存参数摘要、状态及结果。并发请求通过唯一约束或原子状态转换只允许一个执行者，其余等待或返回已有结果。过期策略应与业务重试窗口一致，防止键已删除后旧请求再次产生副作用。

**常见追问：** 取消后重新提交是重试还是新操作？

**追问参考回答：** 先看业务意图是否相同，以及旧操作是否真的撤销。相同意图且状态未知应沿用原键查询；已确认撤销后发起新的业务操作可用新键，并关联原记录。不能只因客户端重新点击就生成新键。

**验证方式：** 并发发送同一键并检查只产生一个业务副作用。

### 52. 工具已执行成功，但结果未写入状态，如何恢复？

**面试回答示例：** 工具执行成功但本地状态没写入，是外部副作用与本地持久化之间的一致性问题。我会在执行前记录操作意图和幂等键，执行后保存回执及状态。恢复时先查询操作记录或外部系统，确认是否已完成，而不是直接重新调用。例如退款超时后，应查退款单和账本。若无法确认，就标为待核实并进行对账或人工处理。关键是允许状态暂时不确定，同时防止重复产生业务副作用。

**核心回答：** 这是外部副作用与本地持久化之间的一致性问题，需要操作记录、幂等键与状态查询。

**展开要点：** 执行前写入操作记录与稳定标识，执行中状态保留为 pending 或 unknown，成功后再保存回执及业务结果。进程崩溃恢复时先查对端状态或按同一幂等键重试。若外部效果不可逆且缺少查询，应转入人工对账。Checkpoint 能恢复计算过程，却不能消除“对端已成功、本地未记录”的时间窗口。

**常见追问：** 事务 outbox 能保证外部服务只执行一次吗？

**追问参考回答：** 不能单独保证。事务 outbox 使本地业务状态与待发送事件原子保存，但消息可能重复投递；外部服务仍需幂等或去重，并处理发送后确认丢失的情况。

**验证方式：** 在对端成功后、本地保存前注入崩溃，检查恢复不会重复扣款。

### 53. 多个工具如何并行执行并处理部分失败？

**面试回答示例：** 多个工具可以并行，但前提是彼此没有数据依赖，而且业务允许并发。例如独立资料检索可以并行，先查订单再根据状态退款则不能并行。我会限制并发数量，对每个调用单独记录成功、错误和超时，避免一个异常丢掉全部结果。部分失败后，根据验收要求选择局部重试、降级返回或停止。涉及写操作时还要考虑补偿与幂等，不能把并发任务汇总成功当成所有业务都已完成。

**核心回答：** 只并行无依赖且允许并发的任务，限制并发并逐个收集结果与错误。

**展开要点：** 根据依赖图找出可并行的读任务，为每项设置独立超时与总并发上限，并结构化保存成功、失败和超时结果。关键证据缺失时不能生成确定结论，可选数据失败则按业务规则降级。并行写操作还需检查资源冲突；汇总时按任务标识而非完成顺序合并，避免结果错位。

**常见追问：** 一个工具很慢，是否一定等待全部完成？

**追问参考回答：** 不一定。可选结果可在 deadline 后放弃并标记缺失；关键结果必须成功、找到替代来源或明确失败。提早返回时应取消不再需要的子任务，并记录已发生的副作用。

**验证方式：** 模拟成功、超时和业务错误组合，验证部分结果策略。

### 54. 用户取消任务后，如何处理后台执行？

**面试回答示例：** 用户取消任务后，我会把取消信号从入口传递到编排、模型请求和工具执行，并停止尚未开始的步骤。正在运行的工具是否可中断，需要看实际能力；已经发生的外部操作不能因为取消就自动撤销。系统应记录取消时间、完成步骤和未确认结果，必要时提供后续对账或补偿。例如取消报告生成可以停止后续写作，但已提交的退款仍需查询状态，向用户明确实际进展。

**核心回答：** 取消需从 API 传播到编排、模型请求和工具执行，并把业务状态与已发生的副作用记录清楚。

**展开要点：** 取消请求首先更新持久化状态，再向运行节点发送取消信号，阻止后续工具和子任务启动。支持中断的网络调用传播取消，不支持的外部操作继续追踪最终状态。界面要区分“请求取消”“已停止计算”和“外部操作已完成”，不能简单显示全部撤销。补偿操作也应独立记录并满足权限要求。

**常见追问：** 进程已取消等待，但外部退款仍成功怎么办？

**追问参考回答：** 把退款成功作为真实业务结果保存并告知用户，停止剩余工作；只有业务支持且获授权时才执行补偿。取消等待并没有撤销远端操作，不能再次退款或直接覆盖为失败。

**验证方式：** 取消等待中的调用，检查没有新步骤执行且结果可对账。

### 55. 你的智能体系统中，审核人员觉得文件写得不好，需要让他重新执行，怎么实现？

**面试回答示例：** 人工审核应作为可持久化的暂停状态，保存待审文件版本、当前任务、审核意见和允许操作。审核人员提出修改后，将反馈作为明确输入恢复执行，只重做需要调整的部分，再产生新版本供复核。审批必须绑定具体产物和操作，不能拿旧版本的批准执行新内容。重启后也应能够恢复待审任务，并处理重复反馈。这样审核形成清晰闭环，而不是靠聊天记录中的一句修改意见重新跑全部流程。

**核心回答：** 将人工审核作为持久化的暂停状态，保存待审版本、具体操作和审批人，收到反馈后恢复。

**展开要点：** 审核节点保存产物 ID、版本、待批准动作、反馈和允许审批人，而非阻塞一个内存线程。批准后继续指定版本；驳回后生成修订版本并重跑相关步骤，原版本保留审计。若暂停恢复会重放节点，把不可重复副作用移到可安全执行的位置，或使用幂等记录；新版内容必须重新审核。

**常见追问：** 审批等一天期间进程重启怎么办？

**追问参考回答：** 使用持久化任务状态和 Checkpointer，审批接口按任务 ID 找到待审版本并校验身份，恢复时加载保存的反馈和状态。进程重启不应丢失待审记录，也不应自动批准。

### 56. 用户对中间结果不满意，怎么让某个节点重新执行？

**面试回答示例：** 重跑某个节点时，我会先找到合适的状态快照，再创建新的执行分支，注入用户反馈，重跑目标节点及依赖它输出的下游步骤。例如修改分析结论后，需要更新报告，但未受影响的数据查询可以复用。还要区分纯计算与外部副作用，已经发送或提交的操作不能随便重复。旧分支与产物应保留，方便比较和回滚。最终检查新结果符合意见，也没有继续使用过期的下游输出。

**核心回答：** 从合适的 Checkpoint 派生新执行分支，注入修改意见，重跑目标节点及依赖它的下游节点。

**展开要点：** 先确认用户要修改哪一份产物，再从相关节点之前的状态派生新分支。依赖图决定哪些下游结果失效，未受影响的检索、解析等结果可复用，但需检查输入版本。文件导出、消息发送等外部动作不能通过回退 Checkpoint 撤销；新分支使用新的产物版本和明确的写操作记录。

**常见追问：** 如何处理已经发送给用户的旧文件？

**追问参考回答：** 保留旧版本并标记已被新版替代，向用户提供清楚的修订关系；必要时按业务能力撤回或失效旧链接。不能假定重跑后用户已经收到或保存的旧文件会自动消失。

### 57. 用LangGraph做了多轮对话Agent，重启后记忆全丢，怎么解决？

**面试回答示例：** 多轮 Agent 重启后丢失记忆，通常需要检查状态是否只保存在进程内。我会配置持久化 Checkpointer，用稳定的线程标识保存和恢复会话状态，并验证重启后能继续执行。跨会话偏好等长期信息则放在 Store 或独立服务，不能混同为一次执行快照。还需要按用户和租户隔离，管理并发更新、版本兼容和过期数据。工具的真实状态仍要核查，恢复消息并不等于恢复所有外部操作。

**核心回答：** 线程内状态使用持久化 Checkpointer，并按稳定 thread_id 恢复；跨会话记忆使用 Store 或独立记忆服务。

**展开要点：** 内存保存器只适合单进程演示，生产需选择持久化后端，把消息、节点状态和暂停位置关联到稳定线程。恢复请求先检查线程属于当前用户或租户，再读取状态；长期偏好等记忆单独管理。还需定义并发写入、数据库迁移、过期清理和版本兼容策略，避免持久化后仍无法安全恢复。

**常见追问：** 两个实例同时恢复同一线程怎么办？

**追问参考回答：** 采用框架后端明确支持的并发策略，或在应用层用租约、锁或乐观版本号防止双重推进。重复请求需要去重，租约失效后接管也要检查外部副作用，不能只相信 thread_id 唯一。

## 安全与多租户隔离（第 58—60 题）

### 58. 安全控制主要做什么？

**面试回答示例：** Agent 安全控制要贯穿输入、数据访问、工具执行和输出。外部文档可能含恶意指令，因此只能作为数据；工具需要最小权限、参数检查和受限执行环境；检索与记忆必须按用户和租户隔离；日志和输出还要防止敏感信息泄露。涉及重要写操作时，审批应绑定具体参数和对象。Prompt 可以表达规则，但不能替代程序权限。测试也要覆盖恶意资料、越权请求和边界参数等实际攻击路径。

**核心回答：** 安全控制要覆盖输入与外部内容、工具授权、数据访问、执行隔离和输出泄露。

**展开要点：** 把模型输出视为待验证请求：检索按权限过滤，工具按认证身份授权，代码或文件操作放在受限环境中，返回结果检查敏感字段。对退款、发送邮件等动作设置参数限额和审批，审计谁在何时基于哪些证据执行。安全控制需落实在可信程序和数据层，Prompt 只说明行为要求。

**常见追问：** 工具返回中出现“忽略之前指令”怎么办？

**追问参考回答：** 把该内容视为不可信数据，不允许其改变系统指令或权限。可标记可疑来源、隔离内容，并继续依据原任务执行；即使模型误听从，也必须在工具执行侧阻止越权动作。

### 59. 外部文档或工具结果含恶意指令，如何防护？

**面试回答示例：** 外部文档里的恶意指令属于不可信输入，我会让系统明确区分任务指令和参考数据，并限制文档内容对工具选择及授权的影响。更关键的是在执行侧验证权限和参数，即使模型被诱导，也无法直接读取其他用户数据或执行越权操作。可以增加来源标记、可疑内容检测和敏感动作审批，但单靠过滤关键词不够。评测时构造带恶意指令的文档和工具结果，检查实际动作与数据访问是否受控。

**核心回答：** 把外部内容作为数据处理，限制其影响控制指令和工具授权，并依靠执行侧权限边界。

**展开要点：** 提示词注入常通过检索文档、网页或工具结果把恶意指令伪装成操作要求。将来源与可信指令分开，减少敏感数据进入上下文；工具只开放必要目标和参数，外部访问设置目的地限制。检测、输出检查与审批可以降低风险，但应通过伪造身份、隐藏指令和数据外传样本验证执行边界。

**常见追问：** 攻击者让 Agent 把客户数据发到指定 URL 怎么办？

**追问参考回答：** 任意目标 URL 不能直接获得发送权限。出站工具按域名及数据范围校验，并使用最小权限；敏感数据发送需要具体审批。拒绝请求时不要把客户数据或密钥包含在错误反馈中。

**验证方式：** 加入隐藏指令、伪造系统消息和数据外传用例。

### 60. 多租户 Agent 如何隔离检索、记忆和工具？

**面试回答示例：** 多租户隔离要从可信身份开始，租户标识由认证系统提供，不能相信模型参数或用户随意填写的字段。这个作用域应贯穿检索过滤、记忆键、工具查询、产物存储、缓存和审计。例如相同问题的缓存也必须考虑租户与权限，否则可能返回他人的内容。执行工具时再次做服务端校验，并测试跨租户查询和标识篡改。不能只在 Prompt 中要求保密，或只在最终输出阶段过滤。

**核心回答：** 使用可信身份建立租户作用域，贯穿检索过滤、存储键、工具执行、缓存和审计。

**展开要点：** 租户身份从可信认证上下文取得，贯穿文档检索、长期记忆、任务状态、对象存储、缓存和工具服务。资源键包含作用域但不能只依赖键名，直接读取 ID 时仍要鉴权。测试需覆盖相同订单号、猜测其他线程 ID、跨租户缓存命中及历史日志访问，防止只在主查询接口做隔离。

**常见追问：** 用户猜到另一个 thread_id 能否恢复对话？

**追问参考回答：** 不能。thread_id 只是定位对话的标识，恢复接口必须根据可信身份校验线程归属和访问权限；未授权请求应拒绝，并避免泄露该线程是否存在或其内容。

**验证方式：** 以其他租户的 ID 请求文档、线程和产物，断言全部拒绝。

## 多 Agent 协作与 A2A（第 61—65 题）

### 61. 单Agent和多Agent之间怎么选？

**面试回答示例：** 我会先建立单 Agent 基线，再判断多 Agent 是否带来明确收益。如果任务可以拆成独立专业工作、需要不同权限或可以并行，多 Agent 可能合适；如果只是同一模型换几个角色聊天，协调成本可能高于收益。例如独立资料核查与写作可以分开，但仍需统一验收。比较时看成功率、延迟、成本和错误传播，同时明确各 Agent 的输入输出、责任边界和失败处理，避免增加不可控的交互轮次。

**核心回答：** 先建立单 Agent 基线；当专业能力、权限隔离或独立并行任务带来可测收益时考虑多 Agent。

**展开要点：** 先用一个 Agent 配合多个专用工具解决任务，只有子任务确实独立、需要不同权限或专业上下文时才拆成多 Agent。例如资料检索与代码测试可以独立运行，再由主节点验收。为每个角色规定产物和工具范围，并测量合并错误、通信 Token 和等待时间；角色越多，协调负担也越大。

**常见追问：** 同一模型换多个角色能解决什么，不能解决什么？

**追问参考回答：** 不同角色提示可能改善分工和检查覆盖，但同一模型的知识缺口及错误往往相关。独立工具、证据和测试更能增加有效信息，不能把多个角色的相互赞同当成正确性保证。

### 62. 多 Agent 常见协作模式有哪些？

**面试回答示例：** 常见多 Agent 模式有主管分派、顺序交接、并行专家汇总和对等协作。我会根据任务依赖选择：独立分析适合并行，明确阶段适合顺序，有动态分配需求可以由主管协调。无论采用哪种模式，都需要任务标识、结构化交付、超时与验收机制。例如多个专家给出冲突结论时，汇总者要检查证据，而不是简单投票。还要限制通信和循环次数，防止协作本身消耗大量成本。

**核心回答：** 常见协作模式是 Supervisor-Worker、顺序交接、并行专家汇总和对等协作。

**展开要点：** Supervisor-Worker 由主节点分派并验收，顺序交接适合阶段性产物，专家并行适合独立角度分析，对等协作则需要额外协调规则。每种模式都应定义最终决策者、冲突处理和最大交互轮次。结果争议时回到证据或测试，而不是无限投票；共享写操作由明确执行者承担。

**常见追问：** 一个子 Agent 失败时整体如何降级？

**追问参考回答：** 必需子任务可重试、切换实现或整体失败；可选任务可以保留其他结果并明确缺失。降级条件应预先定义，主 Agent 不能自行编造失败子任务的结论。

### 63. 你的主智能体和子智能体之间是怎么交互的？

**面试回答示例：** 主智能体与子智能体之间，我会用结构化任务消息交互，包含任务标识、目标、输入引用、限制、期限和验收标准。子智能体返回状态、结果、证据和产物引用，主智能体负责检查完整性并汇总，不把子智能体的成功声明直接当成事实。超时或失败时可以局部重试或重新分配。大型资料通过产物存储共享，避免反复复制上下文，同时保留权限边界和父子调用记录，方便定位责任。

**核心回答：** 主子 Agent 用带任务标识的结构化消息和产物引用交互，主 Agent 负责验收与汇总。

**展开要点：** 任务请求包含 task_id、输入与版本、验收标准、输出格式、权限范围和 deadline；结果包含状态、产物引用、证据及结构化错误。主 Agent 验证结果是否对应当前任务与版本，再合并共享状态。大文件传引用而非全文，降低上下文开销；超时后继续追踪可能已完成的远端任务。

**常见追问：** 如何识别重复返回和处理部分失败？

**追问参考回答：** 使用任务 ID、尝试号及结果版本去重，过期版本不能覆盖新结果。分别记录各子任务状态，对必需结果失败采取预设恢复策略，可选结果失败则标记部分完成。

### 64. 什么是A2A？

**面试回答示例：** A2A 可以理解为跨 Agent 发现能力和协同工作的协议，通过能力描述了解对方能做什么，通过消息、任务和产物表达交互与结果。例如一个研究 Agent 把分析任务交给另一系统，并跟踪执行进度。协议减少了连接方式的差异，但不会自动解决任务正确性、幂等或权限问题。实际接入时我还会验证身份、能力范围、任务状态、取消和超时行为，并对产物进行验收。

**核心回答：** A2A 是跨 Agent 发现与协作协议，Agent Card 描述能力，消息承载交互，任务和产物表达执行与结果。

**展开要点：** 跨团队或跨服务部署的 Agent 可能由不同技术栈实现，A2A 提供能力发现、消息、任务和产物等协作结构。接入时先理解对方的能力描述与输入要求，再按所用版本处理交互状态。协议解决互操作表达，身份认证、队列调度、幂等及最终业务一致性仍是双方服务责任。

**常见追问：** 什么时候本地函数调用已经足够？

**追问参考回答：** 当所有执行单元处于同一应用、接口稳定且不需要跨服务发现或协作时，本地函数或普通内部 API 足够。跨组织、异构服务和长任务协作才可能体现协议价值。

### 65. A2A 的 Task 与 Context 如何关联多轮协作？

**面试回答示例：** Task 表示具体工作单元，Context 用来关联一组相关交互，两者帮助跨轮次定位协作。例如用户补充分析条件时，可以在相关上下文中说明修改内容，并按任务状态继续或建立新的工作单元。应用仍需记录输入版本、任务进展和产物，防止把上一轮结果误用在新要求上。协议标识只是关联基础，不能替代状态持久化、并发控制和幂等处理，实际行为也应按照所用协议版本实现。

**核心回答：** Task 标识具体工作单元，Context 关联一组相关交互；两者用于定位多轮协作而非自动保证可靠性。

**展开要点：** 一次具体工作使用 Task 追踪输入需求、执行状态和产物，Context 用来关联相关消息及任务。例如同一调研上下文内可有独立的资料收集和报告生成任务。客户端使用服务端返回的标识续接，服务器仍需校验归属；关联标识不能替代状态持久化、请求去重或并发控制。

**常见追问：** 同一 Context 新建任务与继续旧任务有什么区别？

**追问参考回答：** 新建任务表示同一相关上下文中的另一项工作；继续旧任务表示向现有工作提供追加信息或按允许状态推进。已结束任务能否继续以及字段细节应依据所用协议版本，不由客户端随意假定。

## Skills 与框架选型（第 66—73 题）

### 66. Skill 与提示词有什么区别？

**面试回答示例：** Prompt 是一次模型输入中的指令或背景，Skill 则通常是可复用的任务说明和资源包，可以包含步骤、资料、脚本和模板。例如报告 Skill 不仅说明写作要求，还提供取数流程和检查清单。Skill 的内容最终可能进入上下文，也可能指导执行代码，因此与 Prompt 并不完全割裂。我会在重复任务和团队复用场景使用 Skill，同时明确适用范围与版本。它提供流程知识，但不能自行授予执行权限。

**核心回答：** Prompt 是模型输入的一部分；Skill 是可复用的能力说明或资源包，可能包含执行步骤、参考资料、脚本和模板。

**展开要点：** Skill 更像某类任务的可复用操作手册及配套资源，例如报告撰写规范、脚本和模板；Prompt 是某次模型调用的具体输入。Skill 可指导模型何时读取资料、执行脚本和校验结果，但不能自行授予系统权限。编写时明确适用条件、依赖、输入输出和失败处理，让复用收益可测试。

**常见追问：** Skill 与一个固定 Workflow 如何组合？

**追问参考回答：** 固定 Workflow 决定必须经过的节点，Skill 指导某个节点如何完成任务。例如流程强制资料审核和发布审批，Skill 提供章节生成及引用校验方法，执行权限仍由流程控制。

### 67. Skill 包通常包含什么？哪些内容取决于平台？

**面试回答示例：** Skill 包通常包含主说明文件，以及按需使用的脚本、参考资料、模板或其他资源。主说明需要解释适用场景、步骤、输入输出和注意条件，例如先读哪份资料、何时执行脚本、如何检查产物。具体目录名称、发现规则和工具能力取决于平台，不能把一种实现当成通用标准。设计时应减少无关内容，保持引用可定位，并验证脚本和说明一致。维护时还要管理版本和适用边界。

**核心回答：** Skill 常含主说明文件及可选脚本、参考资料、模板和资源，但目录不是固定通用规范。

**展开要点：** 主说明文件应写清任务范围、触发条件、必要输入、操作步骤和验收；脚本承担确定性处理，参考资料提供按需读取内容，模板保证产物结构。包内记录依赖及版本，敏感配置通过运行环境提供。不同平台对文件名、元数据和执行方式有要求，应锁定目标平台后再组织目录。

**常见追问：** 如何测试 Skill 是否被正确触发和执行？

**追问参考回答：** 准备应触发、不应触发、缺少输入和失败恢复样本，检查是否读取正确资料、调用正确能力并产出合格结果。脚本能运行只是基础，还需验证整套任务方法是否有效。

### 68. Skill的加载机制是什么？

**面试回答示例：** Skill 加载通常采用逐步展开：先根据名称和描述判断相关性，再读取主体说明，最后按任务需要加载参考文件或执行脚本。这样可以减少无关内容占用上下文。例如用户要求生成报告时，先选择报告能力，再读取模板和必要业务资料。我会检查描述是否清晰、引用路径是否有效，以及加载后是否遵循任务约束。能力发现并不意味着资源都要一次读入，脚本执行也仍需正常的权限和参数校验。

**核心回答：** 通常先发现名称和描述，再按任务加载主体，最后按需读取引用或执行脚本，减少无关上下文。

**展开要点：** 常见做法先加载名称与简介用于选择，再读取主体说明，最后按步骤读取参考文件或执行脚本。按需加载能减少无关上下文，但引用链仍需控制长度并检查资源版本。内容来源不能提高其授权级别；路径无效或依赖缺失时应给出清楚错误，避免模型凭猜测补全操作规则。

**常见追问：** 同时匹配多个 Skill 时如何决定顺序？

**追问参考回答：** 先按任务目标选择最匹配的 Skill，多个必须使用时根据输入输出依赖排序，检查指令冲突和重复步骤。平台若有明确规则则遵循平台机制，不能仅按名称顺序加载。

### 69. LangChain 的核心组件有哪些？

**面试回答示例：** LangChain 可以提供模型、消息、工具、检索和可组合运行单元等抽象，帮助连接常见应用组件；有状态的复杂执行编排则可以结合 LangGraph。实际开发时，我会根据需求选择最少的抽象，例如检索问答只组合检索、提示、模型和解析，不必引入完整 Agent。框架降低接入成本，但也需要理解消息流、异常传播和版本变化。关键业务逻辑及权限仍要明确实现，并保证每个步骤可观测。

**核心回答：** LangChain 提供模型与消息、工具、检索及可组合运行单元等抽象；LangGraph 提供有状态执行编排。

**展开要点：** 面试可围绕项目数据流介绍组件：消息和模型适配负责调用，Prompt 模板负责输入组织，工具负责动作接口，检索器负责证据获取，解析器负责输出验证，Runnable 负责组合。框架可减少适配代码，但业务身份、事务、账本和对象存储应有稳定边界，避免与某个链对象深度绑定。

**常见追问：** 哪些业务逻辑应留在普通 Python 服务里？

**追问参考回答：** 认证授权、金额计算、事务更新、幂等记录和核心业务规则应留在普通服务里。模型链负责理解与编排，业务服务负责最终约束和可独立测试的真实操作。

### 70. LCEL是什么？

**面试回答示例：** LCEL 是基于 Runnable 接口组合数据流的表达方式，常见链路是输入经过 Prompt、模型和解析器，也可以包含并行或分支。例如同时检索两类资料后汇总，再生成结构化答案。它的价值在于统一组件的调用和组合方式，但需要理解每个阶段的数据形状及错误传播。对于循环、人工暂停和持久化恢复等需求，我会另外评估状态编排方案，而不是仅靠串联表达复杂执行流程。

**核心回答：** LCEL 用 Runnable 接口组合数据流，常见表达为 prompt、model 和 parser 的串联，也可表达并行与分支。

**展开要点：** LCEL 可以把输入整理、Prompt、模型调用和结果解析组合成可复用的数据流，也可以让多个检索器并行后合并。组合前约定各节点输入输出 Schema，错误在适当边界转换为结构化结果。重试应只包裹可安全重放的部分，而不是盲目重跑包含退款、文件发送等副作用的整条链。

**常见追问：** 如何实现超时、重试和输入输出类型校验？

**追问参考回答：** 在模型或工具适配器设置真实请求超时，在编排层设总 deadline；对临时且可安全重放的步骤做有界重试。类型声明辅助开发，运行时仍需用 Schema 或模型对象实际校验。

### 71. LangGraph和普通Chain的本质区别？

**面试回答示例：** 普通 Chain 主要描述输入如何经过多个组件转换成输出，LangGraph 则用状态、节点和边组织执行，适合表达循环、条件分支、暂停和恢复。例如工具调用后可以把观察写回状态，再决定继续还是结束。选择时我会看是否需要明确的状态生命周期和可恢复执行，简单问答仍可用普通组合。即使框架支持持久化，也要正确配置存储和标识，并单独处理外部副作用，不能认为恢复状态就保证业务一致。

**核心回答：** 普通组合链主要描述输入输出的数据流；LangGraph 通过状态、节点和边组织可循环、分支及持久化的执行。

**展开要点：** 图编排明确节点读取和写入的状态，条件边决定下一步，Checkpointer 保存可恢复位置。适合对话循环、人工审批和多分支任务；普通链也能包含分支及并行，只是关注点不同。状态设计应避免存入不可序列化对象，并为并行节点更新同一字段规定合并语义。

**常见追问：** 状态 reducer 在并行写入时有什么作用？

**追问参考回答：** reducer 定义多个状态更新如何合并，例如追加并去重消息、合并子任务结果。它不是自动数据库锁，也不保证外部写操作唯一；还需避免依赖不稳定完成顺序或覆盖关键版本。

### 72. 哪些需求适合 LangGraph？有哪些替代方案？

**面试回答示例：** 任务较长、分支复杂、需要人工介入或重启后恢复时，我会考虑 LangGraph，因为这些需求需要显式状态与控制流。例如报告审核流程可以暂停等待意见，再从保存位置继续。但它不是唯一选择，也可以用普通代码、任务队列或工作流引擎实现。选型要比较团队熟悉度、运维、测试和可观测性，尤其确认恢复与副作用处理是否满足业务要求。简单任务不必为了使用框架增加复杂度。

**核心回答：** 需要长任务、可恢复状态、动态分支或人工介入时可以考虑 LangGraph，但没有普遍“必须用”的场景。

**展开要点：** 长任务需要保存阶段产物，审批需要暂停恢复，动态任务需要循环与条件分支，这些需求可能适合图编排。评估时比较状态模型、持久化能力、团队经验和已有平台。队列与数据库也能实现，但需要自行补充调度、恢复和观测；复杂分布式任务还可考虑专门工作流引擎。

**常见追问：** 为何没有直接用队列和数据库实现？

**追问参考回答：** 可以直接实现。选择框架是因为其状态、分支和暂停恢复机制减少维护工作；若需求简单或已有成熟队列平台，自建更合适。面试应说明实际成本与约束，而不是称某框架不可替代。

### 73. 什么时候不该用LangChain/LangGraph？

**面试回答示例：** 如果只是一次模型调用、固定的确定性处理，或者对性能和供应商特殊能力有严格要求，我可能不用 LangChain 或 LangGraph。原生 SDK 加普通代码往往更容易理解和控制，也能减少适配层。是否使用框架应看它能否节省真实的接入与维护工作，而不是看功能数量。复杂流程仍需状态、重试和观测，但可以独立实现。评估时我会比较开发成本、调试难度和升级风险，再确定最小可用方案。

**核心回答：** 简单调用、确定性处理、极端性能约束或框架无法适配的能力，可能更适合原生 SDK 与普通代码。

**展开要点：** 单次模型调用、稳定的两个工具或严格受控的数据处理，用原生 SDK 和少量代码可能更直观。若框架隐藏重试、序列化或调用细节，反而增加排障难度。先保持模型适配、工具服务、状态和日志接口清晰，再判断抽象是否减少重复工作；避免因为框架热门而引入不需要的层级。

**常见追问：** 什么时候从原生实现迁移到框架？

**追问参考回答：** 当模型适配、组件组合、状态恢复等重复代码增长，且框架确实满足需求时再迁移。先做一个代表性任务验证错误处理与可观测性，保留业务服务边界，避免一次重写全部系统。

## 评测、观测、性能与发布（第 74—82 题）

### 74. 如何构建 Agent 离线评测集？

**面试回答示例：** Agent 离线评测集应包含任务描述、初始环境、允许动作、验收标准和评分方式。我会从真实任务及失败案例抽样，覆盖普通成功、缺信息、工具故障和权限边界，使用可重置环境保证复现。业务状态和确定性结果优先用程序评分，开放文本再结合证据与人工判断。还要固定数据版本，保留独立测试集，防止根据评测题过度调参。模型升级后用相同任务比较效果、成本和轨迹。

**核心回答：** 从真实任务和失败样本建立任务、初始环境、允许动作、验收标准和评分器，固定版本并保留隔离测试集。

**展开要点：** 从真实任务和历史失败中构造任务集，为每项保存目标、初始环境、允许工具及成功条件。覆盖正常、缺失信息、权限边界、重复调用、取消和恢复等场景；将开发集与保留测试集分开。执行环境用沙箱或模拟服务避免真实副作用，记录配置和随机性，并针对随机模型多次运行评估稳定性。

**常见追问：** 如何避免评测题进入训练或 Prompt 示例？

**追问参考回答：** 按时间或来源隔离测试集，限制其访问并记录样本用途。训练、合成数据和 Prompt 示例只使用开发集，最终测试集用于独立验收；近重复样本也要检查，不能只按文件名划分。

**验证方式：** 按任务族报告成功率与失败原因，审查模型评分与人工评分差异。

### 75. 如何评价最终结果、调用轨迹和环境状态？

**面试回答示例：** 评价 Agent 不能只看最终回复，需要同时检查回答、调用轨迹和环境状态。回答看是否正确、有证据且符合要求；轨迹看工具选择、参数、权限和是否存在无效循环；环境状态核查业务是否真正完成。例如模型说退款成功，但账本没有记录，就不能判为成功。评分标准应事先定义，并记录必要证据。这样可以识别碰巧答对但过程危险的情况，也能区分表达问题与实际执行问题。

**核心回答：** 最终回答评价表达与证据；轨迹检查工具、权限和效率；环境状态核实业务是否真正完成。

**展开要点：** 结果评分看答案和产物是否满足要求；轨迹评分看是否选择合理工具、遵守审批和预算；环境评分核查数据库、文件和外部操作的最终状态。例如退款解释正确，但账本重复写入仍是失败。评分器应允许合理替代路径，并把严重安全违规单独处理，不能靠其他高分抵消。

**常见追问：** 怎样识别合法的不同执行路径？

**追问参考回答：** 按任务约束和必要里程碑判断，不要求所有调用与参考轨迹逐步一致。只要最终状态正确、证据充分且不越权，不同检索顺序或工具组合可以通过；违规动作则必须单独判失败。

**验证方式：** 对“说成功但未执行”和“正确执行但文字错误”分别计分。

### 76. 如何追踪模型、工具和子任务调用？

**面试回答示例：** 我会用统一的请求标识关联整个任务，再用执行标识和父子步骤记录模型、工具及子任务调用。每一步记录开始结束时间、输入输出摘要、版本、状态、错误和用量，并关联产物引用。这样失败时可以看到是排队、模型、工具还是子任务造成延迟。日志需要脱敏和访问控制，不能为了观测保存全部敏感内容。对于重试与恢复，要保留分支关系，便于还原一次业务操作的真实经过。

**核心回答：** 用 trace_id 关联一次请求，run_id 标识执行分支，各模型或工具步骤记录父子 span。

**展开要点：** 为一次任务分配稳定 run_id，将模型、工具、检索和子任务作为关联的 span，记录开始结束、输入摘要、版本、错误类别、token 与费用。并行任务保存父子或关联关系，恢复事件沿用原任务标识并注明尝试号。日志需要脱敏和访问控制，不能为了排障把密钥和完整客户数据全部记录。

**常见追问：** 如何追踪人工审批后的第二天恢复？

**追问参考回答：** 持久化任务 ID、线程 ID 和审批版本，第二天恢复时创建新的执行段并关联原任务及待审批记录。保留暂停、审批和恢复事件，不能仅依赖原进程内存中的 trace 对象。

**验证方式：** 从最终结果能定位到对应证据、操作和审批记录。

### 77. 成功率下降时，如何区分模型、Prompt、工具和数据问题？

**面试回答示例：** 成功率下降时，我会先按时间、模型版本、Prompt 版本、工具版本和任务类型切分指标，判断变化从哪里开始。再选取失败轨迹复现，检查输入、检索、调用参数和工具返回。通过固定其他条件、替换某一组件来验证原因，例如旧 Prompt 配新模型是否仍失败。也要排查数据分布变化和评分规则变动。修复后做针对性回归，而不是只看整体平均值恢复，忽略某类关键任务持续退化。

**核心回答：** 按时间和版本切分指标，选取失败轨迹，逐层复现并通过受控替换定位原因。

**展开要点：** 先确认下降发生在哪些任务类型与时间段，再检查近期模型、Prompt、工具 Schema、依赖和数据更新。对同一失败输入分别固定证据、模拟工具和替换模型，缩小故障层。区分无法召回、调用失败、参数错误和生成错误；用历史样本回放修复效果，不凭一次重新运行成功判断问题已解决。

**常见追问：** 一次改了模型和 Prompt，如何归因？

**追问参考回答：** 优先分别运行“旧模型＋旧 Prompt”“新模型＋旧 Prompt”“旧模型＋新 Prompt”“新模型＋新 Prompt”。比较主效应和交互问题；若环境也变化，需进一步固定数据与工具版本。

**验证方式：** 旧版本与新版本跑同一隔离数据集并比较失败类别。

### 78. 客服 Agent 答非所问或编造事实，如何定位与修复？

**面试回答示例：** 客服 Agent 答非所问或编造事实，我会从真实失败样本检查意图识别、业务路由、知识版本、检索证据和实际上下文。如果正确材料没召回，优先修检索；材料充分但回答外推，就加强证据约束与核验；涉及实时订单，则必须查业务系统。信息不足时允许澄清或转人工。修改后用可答、不可答和历史失败样本回归，检查正确率与拒答表现，避免靠笼统提示掩盖具体问题。

**核心回答：** 先用真实失败样本定位知识、检索、上下文、生成和业务路由问题，再做有指标的修复。

**展开要点：** 客服失败可以先看意图是否识别正确、订单是否匹配、政策是否有效及证据是否完整。对每条关键承诺核查来源，例如退款时间不能由模型自由猜测。缺少必要信息时澄清，政策冲突时转人工；数字和资格由业务服务计算。修复应针对具体失败层，而不是只加一句“不要幻觉”。

**常见追问：** 如何构造上线前回归集并验证修复？

**追问参考回答：** 将真实错例转为脱敏样本，再加入相近正常、不可答、冲突政策、越权订单和注入问题。固定环境比较修复前后正确率、引用支持与拒答质量，并确认没有重复退款等状态错误。

### 79. 如何缩短 Agent 的关键路径？

**面试回答示例：** 缩短关键路径需要先测量排队、模型输入处理与生成、工具访问、检索和人工等待的耗时。我会优先优化占比最大的环节，例如并行独立查询、减少无效模型轮次、压缩工具结果或缓存稳定资料。缓存必须考虑版本和权限，提前执行也不能触发未授权副作用。优化后同时比较任务成功率和延迟分布，特别关注慢请求。不能只追求更早输出第一段文字，却让实际完成时间和错误率变差。

**核心回答：** 拆分排队、模型 prefill/decode、工具 I/O、检索和审批等待，先优化占比最大的环节。

**展开要点：** 先通过 trace 找到耗时最长的依赖路径，区分排队、模型 prefill、生成、检索和工具等待。并行独立查询，减少无效轮次，缓存版本明确且可授权的数据，压缩无关上下文。总延迟与首个可见输出分别统计；降低输出长度或选择轻量模型需同时检查质量，不能只追求界面看起来更快。

**常见追问：** 并行为什么可能提升成本却不降低延迟？

**追问参考回答：** 并行任务可能受共享限流或硬件争用而排队，最终仍等待最慢的必需结果；非关键任务并行也不缩短关键路径。重复上下文和更多请求会增加费用，因此先分析依赖与资源瓶颈。

**验证方式：** 记录步骤依赖和耗时，对比关键路径变化。

### 80. 如何比较每成功任务成本？

**面试回答示例：** 每成功任务成本可以用同一任务集上的总运行成本除以成功任务数计算，失败和重试消耗也必须计入。成本不仅是模型 Token，还可能包含工具、检索和基础设施使用。比较两个方案时，需要统一成功标准、任务分布和统计范围，同时报告质量、延迟和失败率。例如便宜模型若导致更多轮次和重试，最终未必更省。这个指标用于衡量实际交付效率，不能通过放宽成功定义降低成本。

**核心回答：** 在相同任务集和成功标准下，总运行成本除以成功任务数，同时报告失败、延迟与质量。

**展开要点：** 每成功任务成本可按评测窗口内全部模型、工具和必要基础设施费用除以成功任务数估算，失败和重试费用也计入。同时报告成功率、延迟及高风险错误，避免将低成本部分完成误当成功。区分固定成本与增量费用，并注明成功定义和计费口径，才能比较不同模型及架构。

**常见追问：** 不同难度任务如何避免平均值误导？

**追问参考回答：** 按任务难度、长度和工具类型分层报告，并固定各类任务权重。同时提供失败率和成本分布，防止简单任务数量变化掩盖复杂任务的退化。

**验证方式：** 按任务族比较成本与成功率，说明样本量和波动。

### 81. 模型或 Prompt 升级后如何做回归？

**面试回答示例：** 模型或 Prompt 升级前，我会固定任务集、初始环境和评分规则，用旧版与新版分别运行，比较成功率、工具参数、证据支持、安全、成本和延迟。历史失败及关键业务案例需要重点回归，不能只看平均分。若多项组件同时变化，应拆开验证，便于定位收益与退化。通过离线测试后再做小流量验证，并保留版本记录及回滚配置。上线标准要事先明确，避免看到结果后随意调整门槛。

**核心回答：** 固定任务集与评分规则，比较旧新版本的效果、安全、成本和延迟，并重点检查历史失败样本。

**展开要点：** 回归包应版本化模型、Prompt、工具 Schema、代码、知识快照和评分器。先运行固定任务集与历史失败集，再检查结构化输出、权限、恢复、成本和延迟。对随机系统进行多次运行，并保留未用于调优的验收集；离线通过后仍用受控灰度验证真实分布，不能只看几条演示。

**常见追问：** 模型别名自动更新时如何发现变化？

**追问参考回答：** 优先使用可锁定的模型版本并记录实际响应元数据；定期运行小型哨兵集监控输出及工具行为。供应商未提供明确版本时，只能通过公告和行为变化检测，不能保证识别所有底层更新。

**验证方式：** 保存可辨识模型版本及响应元数据，建立定期回归。

### 82. 如何灰度发布并在效果下降时回滚？

**面试回答示例：** 灰度发布可以按稳定用户或租户分流，先让少量流量进入新版本，并保持实验归属一致。我会监控任务成功、权限违规、成本、延迟和关键错误，按照预先确定的门槛扩大、暂停或回滚。模型、Prompt、工具配置和索引版本应可追踪，必要时协调切换。回滚只改变后续执行，已经发生的业务操作仍需核查和对账。对长任务还要明确版本固定或迁移策略，防止中途混用不兼容状态。

**核心回答：** 按稳定用户或租户分流，小比例上线，监控任务成功、安全、成本和延迟，按事先门槛暂停或回滚。

**展开要点：** 把模型、Prompt、工具 Schema 和执行逻辑作为可追踪配置版本，先向小范围用户或租户稳定分流。监控成功率、严重错误、延迟和成本，设停止或回滚条件。影子流量应隔离写操作，避免双重执行；回滚不仅切流量，还要确保进行中任务、状态格式和外部操作仍能被正确处理。

**常见追问：** 进行中的任务回滚后由哪个版本恢复？

**追问参考回答：** 任务创建时绑定执行版本，通常由兼容该状态的版本恢复，而非直接用当前默认版本。确需迁移时进行显式状态转换与验证，副作用执行继续使用原操作记录和幂等标识。

**验证方式：** 演练切流、旧任务继续与版本不兼容处理。

## 推理优化与模型部署（第 83—86 题）

### 83. KV Cache是什么？为什么推理离不开它？

**面试回答示例：** KV Cache 保存历史 token 在各层产生的 Key 和 Value，自回归生成新 token 时可以复用，避免反复计算整段历史。新位置仍需要产生自己的表示，并关注缓存中的历史信息，因此它减少重复计算，却不会让长上下文成本消失。缓存会占用显存，规模随序列长度、批量和注意力结构变化。我会结合真实并发与上下文长度评估容量，并区分单请求缓存和跨请求前缀复用，后者还要保证输入匹配及权限安全。

**核心回答：** KV Cache 保存已处理 token 的 key/value，避免自回归生成每一步重复计算历史 K、V。

**展开要点：** 自回归生成中，历史 token 的 K、V 在因果模型的常见实现里可缓存，新 token 只需生成自身表示并读取历史缓存，避免反复计算整个前缀。缓存通常随层数、序列长度、批量、KV 头数和精度增长；只读历史仍有开销，因此长上下文 decode 会受内存带宽和容量限制。缓存不包含对任意修改后前缀的正确结果。

**常见追问：** GQA、前缀缓存和分页管理分别优化什么？

**追问参考回答：** GQA 减少 KV 头数，降低缓存容量及带宽需求；前缀缓存复用匹配的已有输入计算；分页管理减少分配碎片并改善调度。三者解决不同问题，都需要正确的版本及隔离策略。

### 84. 大模型量化是什么？INT8/INT4/AWQ/GPTQ怎么选?

**面试回答示例：** 量化通过降低权重或激活的表示精度减少显存和带宽需求，例如使用较低位宽保存参数。INT8 与 INT4 是精度选择，AWQ、GPTQ 等是不同的量化方法，实际效果依赖模型、校准数据、硬件和执行内核。我会先验证任务质量与工具调用表现，再测试真实负载下的吞吐和延迟。位宽更低不代表一定更快，也可能带来精度损失。选型要同时考虑部署支持、转换成本与维护风险。

**核心回答：** 量化降低权重或激活表示精度，以换取显存、带宽或计算收益，实际收益依赖硬件和内核。

**展开要点：** 量化将权重或激活映射到较低精度表示，使用缩放等参数近似恢复数值；具体方法可能只量化权重，也可能覆盖激活或缓存。AWQ、GPTQ 常用于权重量化，但仍需匹配模型和推理内核。用真实任务检查生成、工具参数和长文本质量，同时测显存、吞吐和延迟，不能仅看模型文件大小。

**常见追问：** 为什么更低位宽未必更快？

**追问参考回答：** 硬件未支持相应低位宽内核、反量化开销大、算子未融合或任务处于计算瓶颈时，低位宽可能不更快。要在实际硬件、批量和序列长度下测量。

### 85. 讲讲MOE的核心思想及挑战。

**面试回答示例：** MoE 的核心是为每个 token 选择部分专家参与计算，让总参数量和每次激活的计算量部分分离。路由器决定使用哪些专家，再汇总结果。它可以在有限激活计算下增加模型容量，但不代表部署显存一定小，因为很多专家权重仍需存储。主要挑战有负载不均、路由稳定、跨设备通信和专家利用率。评估时要观察真实吞吐、延迟与内存需求，并考虑任务分布变化对路由和性能的影响。

**核心回答：** MoE 用路由器为 token 选择部分专家，使总参数量与单次激活计算量部分解耦。

**展开要点：** MoE 层通常用路由器为 token 选择少量专家参与计算，使总参数容量与每 token 激活计算量部分解耦。部署仍可能需要保存全部专家权重，并处理负载不均、跨设备通信和路由开销。训练需控制专家利用率；推理要考虑不同 token 路由造成的执行波动，不能把激活参数量当成完整资源需求。

**常见追问：** 为什么 MoE 的延迟受部署拓扑影响？

**追问参考回答：** 专家分布在不同设备或节点时，需要传输 token 表示并汇总结果；带宽、互连延迟和负载均衡都会影响耗时。相同模型在单机多卡和跨节点部署下可能表现不同。

### 86. 自托管大模型推理框架如何选型？

**面试回答示例：** 自托管推理框架选型，我会先确认模型结构、量化格式、硬件和所需接口是否支持，再比较真实负载下的首段延迟、生成速度、吞吐及显存。候选可以包括 vLLM、SGLang 和 TensorRT-LLM 等，但不能仅凭名字判断最好。Agent 场景还需测试工具调用、结构化输出、长上下文和取消行为。最后考虑部署、监控、版本升级与团队维护能力，在效果满足要求后选择整体成本合适的方案。

**核心回答：** 自托管推理可比较 vLLM、SGLang、TensorRT-LLM 等方案，选择应按模型支持、硬件和负载验证。

**展开要点：** 按目标模型、量化格式、硬件与业务并发测试框架，关注连续批处理、缓存管理、长上下文、工具输出和可观测性。将请求分为短问答、长输入和长输出，分别测首 token 延迟、总延迟、吞吐及显存。压测覆盖排队、取消、错误恢复和版本升级，避免只用理想批量评估线上体验。

**常见追问：** prefill 与 decode 的瓶颈有什么区别？

**追问参考回答：** prefill 并行处理输入序列，常较偏计算密集；decode 逐 token 生成，常更受权重与 KV 读取、带宽和调度影响。具体瓶颈会随模型、批量、长度与硬件改变，应实测。

## 附录：Transformer 与 BERT（第 87—103 题）

### 87. 解释一下 Transformer 里 attention 的完整计算流程

**面试回答示例：** Attention 的计算先把输入通过可学习投影得到 Q、K、V，再计算 Q 与 K 的点积，并除以键维度的平方根控制分数尺度。接着在 Softmax 前加入因果或填充掩码，沿允许关注的位置归一化，最后用这些权重加权求和 V。多头场景中，各头独立计算，再拼接并做输出投影。可以把 Q 理解为当前查询、K 为匹配依据、V 为汇总内容，但这只是功能解释，具体表示都是训练得到的。

**核心回答：** 输入 X 通过可学习矩阵投影得到 Q、K、V，计算 Attention(Q,K,V)=softmax(QKᵀ/√dₖ+M)V，其中 M 是掩码。

**展开要点：** 单头注意力先计算 Q=XW_Q、K=XW_K、V=XW_V，再将 QKᵀ 除以 √dₖ，加掩码后沿 key 维度执行 Softmax，最后乘 V。多头注意力分别完成这些步骤，拼接后做输出投影。随后进入残差、归一化与 FFN，具体顺序依模型而定。要区分注意力权重与最终表示，掩码屏蔽的是不可关注的位置。

**常见追问：** Q、K、V 的形状是什么？掩码放在 Softmax 前还是后？

**追问参考回答：** 单头常见形状是 Q：[B,Lq,dₖ]，K：[B,Lk,dₖ]，V：[B,Lk,dᵥ]，权重为 [B,Lq,Lk]。掩码放在 Softmax 前，给屏蔽位置加极大负值；多头实现再增加头维度。

### 88. 什么是多头注意力？

**面试回答示例：** 多头注意力让输入经过多组投影，在不同表示子空间中分别计算注意力，再把各头结果拼接并输出。这样模型能够同时学习多种关联，例如不同位置或特征之间的联系，但不能预先规定某个头一定负责某种语义。固定总隐藏维度时，增加头数通常会降低单头维度，所以更多头不一定带来更好效果。实际还要考虑计算、缓存和实现方式，选择需要通过模型训练与任务评测验证。

**核心回答：** 多头注意力用多组投影在不同表示子空间中并行计算注意力，拼接结果后做线性投影。

**展开要点：** 对总隐藏维度 d_model，多头实现将投影结果按头拆分，每头维度通常为 d_model/h，再汇聚回原维度。优势在于提供多个可学习的关联子空间，而非保证每头负责特定语义。增加头数会改变单头表达容量和运行开销，效果需要训练验证；头数与隐藏维度、位置编码及内核实现也有适配约束。

**常见追问：** 增加头数是否一定改善效果？GQA 和 MQA 改变了什么？

**追问参考回答：** 不一定；固定隐藏维度时更多头意味着更小的单头维度。GQA 让一组 query 头共享 KV 头，MQA 让所有 query 头共享一组 KV，主要减少缓存与带宽；是否保持质量要评测。

### 89. Self attention 和 cross attention 有什么区别？

**面试回答示例：** Self-Attention 的 Q、K、V 来自同一序列，用来建模序列内部的关系；Cross-Attention 的 Q 来自一组表示，K、V 来自另一组表示，用来读取外部信息。例如编码器与解码器结构中，解码器状态作为查询，关注编码器输出。两边长度可以不同，注意力分数矩阵对应查询位置与被关注位置。多模态融合也可以使用类似机制，关键区别是信息来源，而不是是否使用相同的计算公式。

**核心回答：** Self-Attention 的 Q、K、V 来自同一序列；Cross-Attention 的 Q 来自一组表示，K、V 来自另一组表示。

**展开要点：** Self-Attention 根据同一序列生成 Q、K、V，用于序列内部信息交互；Cross-Attention 的查询来自目标表示，键和值来自另一组表示，用于读取外部信息。比如翻译时解码器的目标 token 查询编码器的源语言表示。是否使用因果掩码由任务决定，不是所有 Self-Attention 都限制未来位置。

**常见追问：** Cross-Attention 中两个序列长度不同，矩阵形状如何变化？

**追问参考回答：** 若目标长度为 Lt、源长度为 Ls，Q 为 [B,Lt,dₖ]，K 为 [B,Ls,dₖ]，V 为 [B,Ls,dᵥ]，权重为 [B,Lt,Ls]，输出长度仍为 Lt。两个序列不需要等长。

### 90. Self attention 中 Key 和 value 的数值一样吗？

**面试回答示例：** Self-Attention 中 K 和 V 通常由不同的可学习矩阵投影得到，所以数值一般不同。K 参与与 Q 的匹配，决定关注哪些位置；V 是按注意力权重汇总的内容。虽然它们来自同一输入，但功能和投影参数不同，不能因此认为数值相同。也不能把 K 理解成完全不含语义的标签，因为表示都是学习得到的。是否共享参数是一种架构选择，会限制表达自由度，需要实验评估。

**核心回答：** K、V 通常由不同可学习矩阵投影得到，因此一般不同；K 用于计算匹配权重，V 提供被加权汇聚的表示。

**展开要点：** K 和 V 可以使用相同输入，但通常经过不同参数矩阵投影。K 与 Q 共同决定每个位置的相关性，V 是按相关性权重组合的内容表示。功能区别并不意味着 K 不含语义；共享或不同参数属于架构选择。面试中可用“索引键与被读取的内容”帮助解释，但不能把比喻当成严格数学定义。

**常见追问：** 为什么不直接让 K、V 共用一组参数？

**追问参考回答：** 共用投影可以减少参数，但也将匹配表示与内容表示绑定，降低独立优化空间。是否值得要由模型设计和实验决定，标准注意力通常采用独立投影，并非理论上不能共享。

### 91. 点积注意力为什么除以 √dₖ？

**面试回答示例：** 点积注意力除以键维度的平方根，是为了控制分数尺度，防止维度较大时 Softmax 过于尖锐，导致梯度变小。直观上，若 Q 和 K 的各分量近似独立、均值为零且方差为一，点积方差会随维度增加，缩放后能保持较稳定的尺度。这个推导依赖统计假设，并非每个真实表示都严格满足。它解释了缩放的动机，也提醒我们这里缩放的是 Q 与 K 的点积，而不是与 V 的计算。

**核心回答：** 除以 √dₖ 是为了控制 Q 与 K 点积的尺度，降低 Softmax 饱和导致梯度变小的风险。

**展开要点：** 若 q、k 各分量近似独立且方差为 1，点积是 dₖ 项之和，方差约为 dₖ；除以 √dₖ 后尺度更稳定。未经缩放的 logits 容易过大，使 Softmax 接近极端分布并影响梯度。缩放是一种设计归纳，实际训练中的分量相关性和方差并不完全满足简化推导。

**常见追问：** 不做缩放会怎样？这些统计假设是否严格成立？

**追问参考回答：** 可能出现 Softmax 饱和和梯度减弱，但实际严重程度取决于参数与训练。独立、零均值、单位方差只是解释尺度的近似假设，不是模型训练始终成立的条件。

### 92. 注意力层和全连接层之间的本质区别是啥？

**面试回答示例：** 注意力层主要按内容动态汇聚不同 token 的信息，而位置前馈网络通常对每个 token 独立进行非线性变换。可以理解为注意力帮助位置之间交换信息，前馈网络进一步加工各位置的特征。两者都可能包含线性投影，也都可以改变表示维度，因此不能用是否改变维度区分本质。前馈网络常先扩展再压缩隐藏维度，残差连接则要求相加时形状兼容，具体结构由模型设计决定。

**核心回答：** 注意力按内容动态混合不同 token 的信息；位置前馈网络通常对每个 token 独立地执行非线性特征变换。

**展开要点：** 注意力执行跨 token 的动态加权汇聚，FFN 通常在每个 token 上独立执行相同的非线性变换。典型 FFN 为 Linear→激活→Linear，也可能采用门控结构。两者都能包含投影并保持最终隐藏维度；区别不在“谁改变维度”，而在是否进行跨位置混合及其权重如何产生。

**常见追问：** FFN 为什么先升维再降维？残差连接要求什么形状？

**追问参考回答：** 升维提供更大的中间特征空间，激活或门控增加非线性，再降维回到隐藏维度。残差相加的张量形状要兼容，通常要求相同形状；不匹配时需明确投影，不能直接相加。

### 93. FlashAttention 是什么？它如何优化 GPU 内存访问？

**面试回答示例：** FlashAttention 通过分块计算和在线 Softmax，减少 GPU 显存与片上存储之间的数据搬运，避免把完整注意力矩阵写入显存。它优化的是内存访问与中间结果存储，在数学目标上计算标准注意力，不是通过简单删掉信息获得近似结果。速度提升不意味着稠密注意力的算术复杂度变成线性。它与 KV Cache 也不同，前者优化一次注意力计算，后者复用生成过程中历史位置的 K、V，两者可以配合。

**核心回答：** FlashAttention 是面向 GPU 内存访问的精确注意力算法，减少 HBM 与片上 SRAM 之间的数据搬运和大中间矩阵存储。

**展开要点：** 朴素注意力会产生随序列长度平方增长的中间权重矩阵，反复读写 GPU 高带宽显存。FlashAttention 通过分块将部分计算放在片上 SRAM，并用在线 Softmax 合并块结果，减少中间矩阵存储与数据搬运。它仍计算标准稠密注意力，数学结果与标准公式等价，但浮点运算顺序可能造成细微数值差异。

**常见追问：** 为什么同样的算术复杂度可以明显更快？与 KV Cache 有何区别？

**追问参考回答：** 减少显存访问和中间结果读写能改善实际运行时间，即使算术复杂度相同。KV Cache 复用历史 token 的键值计算；FlashAttention 优化注意力计算及访存方式，两者可以配合。

### 94. decoder-only 与 encoder-decoder 如何取舍？

**面试回答示例：** Decoder-only 用因果语言建模把训练和逐步生成联系起来，适合通用文本生成；Encoder-decoder 则把输入编码与条件生成分开，解码器能够关注编码后的输入。选择不能只看结构名称，要结合任务、已有模型、训练数据和延迟要求，例如翻译与通用对话可能有不同取舍。我会比较可用模型的实际效果和部署成本，而不是认为某种结构在所有任务上都更好。分类和检索也可以选择其他合适的表示方案。

**核心回答：** decoder-only 用因果语言建模统一训练和生成，适合通用文本生成；encoder-decoder 对输入理解与条件生成进行分工，也有适用任务。

**展开要点：** decoder-only 通过因果语言建模预测后续 token，输入与输出可统一为一个序列；encoder-decoder 先编码输入，再由解码器关注编码结果进行条件生成。encoder-only 适合表示学习等任务，是否最优取决于训练数据与使用方式。选择时综合任务、已有模型、质量、推理成本和工程生态，不只依据结构名称。

**常见追问：** 做分类、检索、翻译分别如何选结构？

**追问参考回答：** 分类可用 encoder 或生成模型；检索通常选专门训练的 Embedding 模型；翻译可比较 encoder-decoder 与 decoder-only 的实际质量。已有权重和任务训练往往比架构标签更影响效果。

### 95. RoPE 如何表达位置？长上下文外推有哪些限制？

**面试回答示例：** RoPE 对 Q 和 K 按位置进行旋转，使它们的点积包含相对位置信息，并适合自回归推理。虽然公式能计算更远的位置，但这不代表模型在超过训练长度后仍能可靠理解内容，效果还受频率配置、训练数据和扩展方法影响。位置插值等方法可以调整位置范围，但需要验证质量。我会用跨位置检索、多证据推理和长任务测试评估，而不只看模型是否接受长输入或找到单个关键词。

**核心回答：** RoPE 对 Q、K 做随位置变化的旋转，使点积包含相对位置信息，并方便与自回归推理结合。

**展开要点：** RoPE 将 Q、K 的成对通道按位置旋转，使它们的内积具有与相对位置有关的形式；通常不直接旋转 V。它与绝对位置向量相加不同，便于自回归缓存使用。长上下文扩展还需处理训练中未见位置与频率分布，能计算位置编码并不意味着模型能可靠利用远处证据。

**常见追问：** 位置插值解决什么问题？长上下文如何评测？

**追问参考回答：** 位置插值将更长序列的位置映射到较熟悉的范围，常需结合适配训练及验证。长上下文测试除检索隐藏事实外，还应检查多证据推理、不同位置、冲突干扰、延迟和显存，不能只看单条“大海捞针”。

### 96. RMSNorm(均方根归一化。)比LayerNorm(层归一化)好在哪儿？

**面试回答示例：** RMSNorm 使用均方根缩放输入，没有 LayerNorm 中的减均值步骤，因此计算形式更简洁。二者都能帮助控制表示尺度，但保留的性质和具体操作不同。不能因为少了一个步骤，就断言所有任务效果一定更好，最终还取决于模型结构、训练设置和内核实现。讨论时我也会区分归一化放在子层前还是后，因为这影响残差路径和训练稳定性。选型应以实际训练与推理结果为依据。

**核心回答：** RMSNorm 按均方根缩放，不执行 LayerNorm 的减均值操作，计算更简洁。

**展开要点：** LayerNorm 对特征向量减均值后按方差归一化；RMSNorm 直接按均方根缩放，并通常带可学习缩放参数。RMSNorm 不保证输出零均值，省去部分统计计算，在一些架构中表现良好。选择仍与训练稳定性和实现有关；Norm 的位置与残差结构也会影响优化，不能仅按计算更少判定效果更好。

**常见追问：** Pre-Norm 与 Post-Norm 有什么区别？

**追问参考回答：** Pre-Norm 在子层计算前归一化，残差路径相对直接，常便于深层训练；Post-Norm 在残差相加后归一化。两者训练行为不同，但没有在所有模型和设置中都更优的结论。

### 97. BERT 的 LayerNorm 沿哪个维度归一化？

**面试回答示例：** 对于常见形状为批次、序列、隐藏维度的 BERT 表示，LayerNorm 在每个 token 的隐藏维度上计算均值和方差，再应用可学习缩放与偏移。它不会依赖当前批次中其他样本的统计，因此比较适合序列长度和批量变化的场景。BatchNorm 则通常按通道聚合批次及相关维度，并在推理时使用运行统计。理解时要结合具体张量形状，不能把沿哪个维度归一化简单概括成固定的行或列。

**核心回答：** 对形状 [batch, sequence, hidden] 的常见 BERT 表示，LayerNorm 在每个 token 的 hidden 维度上计算统计量。

**展开要点：** 常见输入形状为 [B,L,H]，LayerNorm 对每个样本、每个 token 的 H 个特征计算均值和方差，学习对应特征的缩放及偏移。它不把不同 token 或不同样本混合来计算统计量。BatchNorm 通常沿批次及空间维度统计通道，序列长度、padding 和小批量会使实现与稳定性更复杂。

**常见追问：** 为什么可变长度序列常采用 LayerNorm？

**追问参考回答：** LayerNorm 不依赖 batch 大小或不同序列样本的统计，每个 token 可独立归一化，训练与推理更一致。padding 仍需在注意力及损失中正确屏蔽，使用 LayerNorm 并不消除这项需求。

### 98. 大模型的分词器是怎么工作的？

**面试回答示例：** Tokenizer 把文本经过对应的预处理和分词规则转换成 token ID，模型实际处理的是这些编号。常见方案有 BPE、WordPiece 和 Unigram，其中 BPE 通过反复合并高频相邻单元构建词表，基础单元可能是字符或字节。部署必须使用与模型匹配的词表、特殊 token 和模板规则，否则输入含义可能改变。不同语言的切分长度也会影响成本与截断，所以预算应基于实际编码结果，不能直接按字数估计。

**核心回答：** Tokenizer 将文本编码为 token ID；常见方案包括 BPE、WordPiece 和 Unigram，具体预处理取决于模型。

**展开要点：** 文本先经过模型指定的规范化、预切分或字节处理，再按词表规则编码为 token ID，并加入必要特殊标记。BPE、WordPiece、Unigram 的词表训练方法不同，推理时必须与权重配套。token 是模型处理单位，不等于字符或词；处理工具 Schema、对话模板和长输入时，要计入实际拼接后的总长度。

**常见追问：** 中英文的 Token 成本为何不同？截断会破坏什么信息？

**追问参考回答：** 不同词表对语言和符号的分解不同，相同字符数可能对应不同 token 数。截断可能删除否定词、单位、例外条款或工具调用结构，因此应按内容边界裁剪并保留关键约束。

### 99. BERT为什么用子词粒度而不是词粒度或字粒度？

**面试回答示例：** 子词粒度在词表大小、序列长度和未知词处理之间取得折中。整词词表可能很大，罕见词难覆盖；逐字拆分又可能让序列过长，弱化常见词片段的整体表示。BERT 使用 WordPiece，把常见片段保留，罕见词拆成多个单元。这样能共享构词信息，但是否覆盖任意字符仍取决于词表和回退方式，不能保证绝无未知 token。选用时还要看语言特点、计算成本及下游任务效果。

**核心回答：** 子词在词表规模、序列长度和未登录词处理之间取平衡，BERT 使用 WordPiece。

**展开要点：** 按词编码会使词表膨胀并遇到未登录词，按字编码则可能使序列变长、削弱常见词组的表示效率。子词把常见片段作为单元，罕见词拆分，在词表容量和序列长度间折中。BERT 的 WordPiece 是否覆盖某字符依赖词表，不能将它与所有字节级 tokenizer 的回退能力混为一谈。

**常见追问：** 子词长度如何影响推理成本？

**追问参考回答：** 相同文本切成更多 token 会增加上下文占用、缓存和推理步骤；训练也需处理更长序列。比较 tokenizer 时应结合语言覆盖与模型效果，不能单靠平均 token 数选型。

### 100. BERT只有encoder的，那么它的mask有哪几种？

**面试回答示例：** BERT 的 mask 需要区分注意力掩码与预训练数据中的掩盖。注意力掩码通常用于排除填充位置，标准双向编码器并不像自回归解码器那样限制读取未来位置。MLM 则选出部分 token 作为预测目标，并对输入做替换或保持原样，这不是同一种机制。实现时应分别检查可关注位置和损失计算位置。若把二者混为一谈，容易错误地认为出现掩盖词就需要因果注意力，或者所有位置都参与预测损失。

**核心回答：** 需要区分注意力掩码与 MLM 数据构造：前者限制可关注的位置，后者指定预测哪些输入 token。

**展开要点：** attention padding mask 防止模型读取填充位置；causal mask 用于限制未来位置，原始 BERT 编码器的双向注意力通常不用因果屏蔽。MLM 则改变部分输入 token 并要求预测原词，属于训练样本构造。输入替换和 attention mask 是不同机制，不能因为名称中都有 mask 就混为一谈。

**常见追问：** MLM 标签中哪些位置参与 loss？

**追问参考回答：** MLM 损失通常只在被选中作为预测目标的位置计算，其他位置以及 padding 的标签设为忽略值。选中位置即使没有替换成 [MASK]，仍可作为预测目标。

### 101. 为什么MLM掩盖比例是15%

**面试回答示例：** 原始 BERT 选取约百分之十五的 token 作为 MLM 预测目标，其中多数替换为掩盖标记，另有少量随机替换或保持原样。这样既提供足够训练信号，又保留较多上下文供模型推断；混合替换也能缓解训练和实际使用之间的输入差异。这个比例是具体训练方案的选择，不能理解为数学上的唯一最优值。其他掩盖比例和策略需要结合数据、模型与计算预算验证，并区分被选中预测和实际被替换的位置。

**核心回答：** 原始 BERT 随机选取约 15% 的 token 作为预测目标，其中约 80% 替换为 [MASK]、10% 随机替换、10% 保持不变。

**展开要点：** 原始 BERT 在选定约 15% 的 token 后，通常将其中 80% 替换成 [MASK]、10% 替换成随机 token、10% 保持不变。这个比例在保留上下文和提供预测任务间折中，不是所有模型通用的最优值。选中比例、替换策略和动态采样都可改动，但应通过任务和训练设置验证。

**常见追问：** 为什么不把所有选中位置都换成 [MASK]？

**追问参考回答：** 预训练经常看到 [MASK]，而实际下游输入一般没有它，会存在分布差异。随机替换及保留原 token 让模型不只依赖标记位置，但并不能完全消除预训练与下游差异。

### 102. [CLS]的作用？在BERT中，它的非线性从哪来？

**面试回答示例：** CLS 是 BERT 中的特殊位置，经过多层双向注意力后可以与其他 token 交互，其最终表示常被用于分类任务。但它不是天然就能完美概括整段文本，表示质量取决于训练目标和任务适配。非线性来自整个网络中的前馈激活、注意力归一化等操作，具体实现也可能包含池化层的非线性变换，不能只归因于一个特殊标记。使用时应比较 CLS、平均池化等方法在实际任务上的效果。

**核心回答：** [CLS] 是可参与全局交互的特殊位置，其最终表示常用于分类，但不是自动保证完美语义聚合。

**展开要点：** [CLS] 是序列开头的特殊 token，其最后层表示可作为分类特征；表示通过多层注意力、FFN 和归一化吸收上下文。非线性来自 Softmax、激活函数及归一化的输入相关计算等；单独的线性投影或固定缩放偏移本身不是非线性。用于分类时，还需说明使用的是原始表示、pooler 还是另行训练的头。

**常见追问：** 直接使用 [CLS] 做语义检索有哪些限制？

**追问参考回答：** BERT 的预训练目标没有直接保证 [CLS] 的向量距离适合语义检索；未经检索或对比训练，效果可能较差。应比较池化方式并使用为检索训练的 Embedding 模型，而非直接假定分类表示可用。

### 103. BERT预训练为什么用warm up？长文本怎么办？

**面试回答示例：** Warmup 在训练初期逐渐提高学习率，可以缓和模型和优化器状态尚未稳定时的剧烈更新，之后再按计划衰减学习率。长文本则是另一个问题，要考虑位置长度限制和注意力成本。我会根据任务采用分段编码、滑动窗口、层级聚合或适配长上下文模型。分类可以汇总分段结果，细粒度问答要保留证据位置。不能认为调整学习率就解决长文本，也不能简单截断而忽略任务所需信息。

**核心回答：** Warmup 在训练初期逐步提高学习率以改善优化稳定性；长文本则需要分段、聚合或适配长上下文模型。

**展开要点：** warmup 在训练初期逐步提高学习率，减轻参数尚未稳定时大步更新的风险，之后再按计划衰减。BERT 的可处理长度受模型配置和训练设置限制，长文档可分段、滑窗或使用适配长输入的模型。段级结果要保留文档位置，分类与问答可采用不同汇总方式，不能简单平均所有片段就解决跨段推理。

**常见追问：** 跨段证据如何合并？分段方案如何避免遗漏？

**追问参考回答：** 检索各段证据并保留标题和相邻关系，再用聚合模型或确定性规则合并。设置 overlap、覆盖检查和跨边界测试，必要时读取父章节；单独片段都不完整时不能直接拼接局部结论。

## 附录：训练、微调与对齐（第 104—115 题）

### 104. 一个大模型是怎么训练出来的？分多少个阶段？

**面试回答示例：** 大模型常见训练路线包括预训练、指令微调，以及偏好或奖励优化，但具体阶段和是否使用强化学习会因方案不同而变化。预训练从大量数据学习语言与知识模式，指令微调帮助模型按任务要求回答，偏好优化进一步调整行为。训练还依赖数据清洗、去重、配比、分布式计算和持续评测。部署前需要检验实际任务及安全边界，不能只看训练损失。对于 Agent 应用，也要单独评测工具选择和参数生成能力。

**核心回答：** 常见路线包括预训练、指令微调及偏好或奖励优化，但实际流程和是否使用强化学习因模型而异。

**展开要点：** 通常先准备并清洗语料、训练或选定 tokenizer，再进行语言建模预训练；随后可做指令微调、偏好优化和安全评测。不是每个模型都经过完全相同阶段，也可能加入领域继续预训练或多模态训练。Agent 项目通常基于现有模型，重点是工具接口、执行环境和评测，不需要从头训练才能实现。

**常见追问：** Agent 的工具使用能力可以怎样训练或评测？

**追问参考回答：** 可以用正确工具选择、参数和反馈样本做监督训练，或在沙箱中基于最终任务结果优化。评测要覆盖调用合法性、业务状态、权限和恢复，不能只看模型是否输出正确工具名。

### 105. 讲讲scaling law（规模定律）和涌现能力。

**面试回答示例：** Scaling law 描述在一定数据和训练条件下，损失与参数量、数据量和计算投入之间的经验关系，可以辅助决定预算怎么分配，但不是规模与所有能力简单成正比。所谓涌现可能表现为某些任务在较大规模后明显改善，也可能受到评分阈值和指标形式影响。因此我会区分连续的底层变化和评测表现的跃升。工程选择仍应看实际任务效果、成本和约束，不能只根据参数数量预测模型是否胜任。

**核心回答：** Scaling law 描述特定条件下损失与参数、数据、计算量之间的经验关系；它不是性能与规模的简单正比。

**展开要点：** 规模定律描述在一定模型、数据与计算范围内，损失随资源规模变化的经验关系，用于指导预算配置。某些能力在指标上看似突然出现，可能与评测阈值、离散评分或任务复杂性有关，不能直接证明存在普遍的临界规模。数据质量、训练配方和评测分布都会影响结论，外推要谨慎。

**常见追问：** 有固定预算时如何平衡模型大小与训练数据？

**追问参考回答：** 先根据可用计算和数据质量做小规模实验，比较参数量与训练 token 的投入收益。数据不足时盲目增大模型可能训练不充分；也应考虑部署成本和最终任务，而非只优化训练损失。

### 106. 微调有哪些方案该怎么选？

**面试回答示例：** 微调选型前，我会明确想改变的是知识获取、输出格式、行为还是领域任务能力。最新资料查询优先考虑 RAG，简单格式要求先尝试 Prompt，稳定的领域行为再比较 LoRA、QLoRA 和全量微调。选择要结合数据质量、计算资源和维护成本，先建立不训练的基线。训练集需要覆盖真实分布与负例，评测也要检查通用能力退化。并非参数更新越多越好，动态业务事实仍需外部可靠数据源。

**核心回答：** 先明确需要改变知识获取、格式、行为还是领域能力，再比较 Prompt、RAG、LoRA、QLoRA 和全量微调。

**展开要点：** 全量微调更新全部参数，参数高效微调只训练 LoRA、Adapter 等新增或部分参数，软提示学习则优化连续提示向量。选择时看任务差异、数据规模、显存、部署和维护多个适配器的需求。先尝试 Prompt、检索和简单基线，再根据失败证据训练，并检查灾难性遗忘及未见样本泛化。

**常见追问：** 什么问题不适合靠微调解决？

**追问参考回答：** 实时事实、访问权限、金额规则和外部系统状态不适合依靠微调保证。数据本身错误或任务定义不清也应先修复；微调不能替代检索、业务校验和执行授权。

### 107. LoRA的原理和核心优势。

**面试回答示例：** LoRA 冻结基座权重，把需要学习的更新表示成两个低秩矩阵的乘积，并配合缩放系数，只训练这部分参数。相比全量微调，它通常减少梯度和优化器状态开销，也方便保存和切换不同任务适配器。基座仍然要参与前向计算，因此不代表训练完全没有显存成本。秩和注入位置决定适配能力与参数量，我会在领域任务和通用能力上一起评测，并验证合并权重或独立加载后的推理行为。

**核心回答：** LoRA 冻结基座，将权重更新写成低秩分解 ΔW=(α/r)BA，仅训练较少适配参数。

**展开要点：** LoRA 冻结原权重 W，为部分线性层学习低秩增量 ΔW=(α/r)BA，其中 A 为 r×d_in，B 为 d_out×r。训练参数从 d_out×d_in 降为 r(d_in+d_out)，通常还可将增量合并回权重。它节省训练参数及优化器状态，但前向激活和基础权重仍需要显存；适配哪些层比只选 rank 同样重要。

**常见追问：** 低秩假设意味着什么？如何验证 rank 足够？

**追问参考回答：** 低秩假设是目标任务所需的有效权重更新可被较低秩近似，不代表原始权重本身低秩。固定数据和训练预算比较多个 rank 的验证效果、成本和泛化，检查增加 rank 是否仍有实质收益。

### 108. 为什么标准 LoRA 通常将 B 矩阵初始化为零？

**面试回答示例：** 标准 LoRA 常让 A 随机初始化、B 初始化为零，这样两者乘积在开始时为零，模型最初仍保持基座行为。第一次反向传播时，B 可以获得学习信号，而 A 的梯度通常因 B 为零暂时为零，随后两者共同更新。如果两个矩阵都设为零，通常会使学习无法有效启动。这个设计针对常见的标准参数化，其他初始化方案可能不同。解释时需要区分初始更新为零和所有可训练参数都为零。

**核心回答：** 标准 LoRA 常用 A 随机初始化、B 零初始化，使初始 ΔW 为零，保留基座初始行为。

**展开要点：** 常见初始化让 A 为随机值、B 为零，使初始 BA=0，模型开始时保持原输出。第一步 B 可从随机 A 接收有效梯度，随后 A 也能更新；这里为零的是参数，不是学习率。还有采用其他初始化的 LoRA 变体，因此应说明讨论的是默认或常见标准设置，而非所有实现。

**常见追问：** 为什么不能同时把 A、B 都初始化为零？

**追问参考回答：** 若 A 和 B 同时为零，乘积对两者的梯度都含另一零矩阵，标准 LoRA 数据损失路径无法启动有效更新。让一个矩阵随机、另一个为零，兼顾初始零增量与可学习性。

### 109. LoRA的压缩比怎么算？秩r一般取多少？

**面试回答示例：** 对于输出维度乘输入维度的权重矩阵，LoRA 增加的参数量是秩乘以输入与输出维度之和，可以与原矩阵参数量比较。例如一个方阵，低秩参数占比随秩增大而上升。但这只是适配参数的比例，不等于整个模型的显存压缩比，因为基座权重、激活等仍需存储。秩没有通用最优值，我会选择几个候选，结合任务复杂度、质量、显存和训练时间评估，也考虑注入哪些层。

**核心回答：** 对于 d_out×d_in 权重，LoRA 可训练参数为 r(d_in+d_out)，可与 d_out×d_in 比较。

**展开要点：** 单个 d_out×d_in 矩阵的 LoRA 参数比例为 r(d_in+d_out)/(d_in×d_out)。例如 4096×4096、r=8 时，新增 65536 个参数，约为该矩阵参数的 0.39%；全模型比例还取决于适配哪些层。rank 没有固定答案，应比较质量与显存、训练时间及多适配器管理成本，参数减少也不等于同倍显存节省。

**常见追问：** rank 增加后的收益如何衡量？

**追问参考回答：** 在相同数据和可比训练设置下观察验证指标增益、过拟合、适配器大小和训练耗时。若更高 rank 只改善训练集，或收益很小，就优先较低 rank，并检查是否应改变适配层。

### 110. 指令微调（Instruction Tuning）和提示学习（Prompt Learning）区别

**面试回答示例：** Instruction Tuning 通常用指令和答案样本更新模型权重或适配器，让模型更好地遵循任务；Prompt Learning 常指学习连续提示参数等方法，可能保持基座冻结。它们与手工写自然语言 Prompt 需要区分。选择取决于可训练参数、任务数量、数据和部署支持，例如轻量任务适配可以评估提示参数，而稳定行为调整可以评估指令微调。最终仍需检查泛化、格式和能力退化，不能只比较训练集损失。

**核心回答：** Instruction Tuning 通常用指令—回答数据更新模型或适配器；Prompt Learning 通常指学习连续提示参数等方法。

**展开要点：** 指令微调通常以指令、输入和目标回答构建训练数据，可全量更新或使用 LoRA；软提示学习则训练连续提示向量，通常冻结模型主体。手写 Prompt 属于无需训练的输入设计，不能与软提示训练等同。选择前需明确“行为需要改变”还是“只是缺少输入信息”，并检查部署端能否支持所选适配方式。

**常见追问：** 什么时候先优化 Prompt，什么时候训练适配器？

**追问参考回答：** 需求尚不稳定、样本少或问题是格式和任务说明时先优化 Prompt。只有重复失败已有可靠标注数据，且输入设计无法解决时，再训练适配器并做独立回归验证。

### 111. 全量微调的显存到底花在哪里？怎么估算？

**面试回答示例：** 全量微调的显存不只用于模型权重，还包括梯度、优化器状态、可能保留的高精度主权重、激活和临时缓冲。我会先根据参数量、数据类型和优化器估算静态部分，再结合批量、序列长度和层结构估算激活，最后用实际训练测峰值。优化器分片、梯度检查点等可以降低部分占用，但有通信或计算代价。不能用推理时的权重大小直接判断能否训练，还要为临时分配和实现差异保留余量。

**核心回答：** 训练显存包括权重、梯度、优化器状态、可能存在的主权重副本、激活和临时缓冲。

**展开要点：** 以一种混合精度 Adam 实现为例，每参数可能包含低精度权重 2 字节、低精度梯度 2 字节、FP32 主权重 4 字节和两份 FP32 优化器状态共 8 字节，合计约 16 字节。7B 参数仅这些状态就约 112 GB（十进制），还未计入激活、临时工作区与通信缓冲。梯度精度、优化器及分片方式会改变估算，应按批量、长度和实际实现测峰值。

**常见追问：** ZeRO、梯度累积和激活检查点分别节省哪部分？

**追问参考回答：** ZeRO 将优化器状态、梯度和参数按阶段分片；梯度累积通过更小微批量达到有效批量，但不减少基础参数状态；激活检查点以重新计算换取较低激活内存。各自节省的对象不同。

### 112. 讲一下RLHF的整体流程。

**面试回答示例：** 经典 RLHF 流程通常先做指令微调，再收集对多个回答的偏好标注，用这些数据训练奖励模型，最后通过 PPO 等方法优化策略，同时限制它偏离参考模型。它把人的偏好转化为训练信号，但奖励模型可能有偏差，策略也可能学会利用评分漏洞。实际需要高质量标注、奖励验证和独立评测。不同方案可以简化或替代部分阶段，因此不能把所有偏好训练都说成一定要包含独立奖励模型。

**核心回答：** 经典 RLHF 路线是 SFT、收集偏好数据并训练奖励模型，再通过 PPO 等方法优化策略并约束偏离参考模型。

**展开要点：** 经典 RLHF 通常先进行指令微调，再采集人类偏好并训练奖励模型，最后用强化学习优化策略，同时以参考模型或其他约束控制偏移。反馈标准需要清楚，并覆盖正确性、安全和表达质量。奖励模型只是人类目标的近似，策略可能利用评分漏洞，因此必须检查真实任务结果而非只看奖励上涨。

**常见追问：** 奖励模型偏差如何影响策略？

**追问参考回答：** 奖励模型偏好冗长、迎合或错误特征时，策略可能放大这些行为。改进标注覆盖、奖励校准和独立验收，并监控奖励提升是否对应真实质量提升，防止奖励投机。

### 113. DPO是什么？为什么它不需要奖励模型？

**面试回答示例：** DPO 使用同一问题下的偏好与非偏好回答，直接优化策略相对参考模型对两者的概率关系，不需要另外训练显式奖励模型，也不需要相同形式的在线采样优化循环。它适合已经拥有可靠偏好对的场景，流程相对简化。但数据质量、覆盖范围和偏好强度仍会影响结果，错误偏好也会被学进去。我会关注分布偏移与通用能力退化，不能因为省掉奖励模型，就认为训练完全没有奖励假设或质量风险。

**核心回答：** DPO 将偏好优化目标转化为对偏好对的直接训练，不需要单独训练显式奖励模型或在线采样循环。

**展开要点：** DPO 直接利用同一输入下的优选与劣选回答，通过相对参考模型的对数概率差构造偏好损失，不必单独训练并调用一个显式奖励模型进行 PPO 式优化。常见实现使用离线偏好数据，但仍可能需要参考策略。数据质量、偏好一致性和分布覆盖决定效果，并非“无需奖励模型就无需可靠反馈”。

**常见追问：** 离线偏好数据与线上任务分布不一致怎么办？

**追问参考回答：** 重新采集接近线上任务的偏好对，保留旧任务防止退化，检查选择标准和困难样本。对新分布做独立评测；只在旧离线数据继续训练可能扩大偏差。

### 114. GRPO是什么？

**面试回答示例：** GRPO 对同一个输入采样一组输出，依据各输出的奖励构建组内相对优势，再用于策略更新，常见实现不需要单独的价值网络。它适合能够比较一组候选并获得较可靠奖励的设置，例如结果可验证的任务。优势在于简化某些训练组件，但仍需要采样成本和可信评分。若整组奖励差异很小，学习信号可能不足；若奖励设计有漏洞，也可能产生投机行为，因此需要独立评测和约束。

**核心回答：** GRPO 对同一输入采样一组输出，以组内奖励构建相对优势，常见实现不使用单独价值网络。

**展开要点：** GRPO 对同一输入采样多条输出，典型组相对优势可表示为 (奖励−组内均值)/(组内标准差＋ε)，再结合策略目标更新。与使用单独价值模型的方案相比，它可减少相应训练开销，但组采样和奖励计算仍有成本。组内奖励相同时缺少有效区分信号；具体裁剪、KL 及归一化方式依实现而异，不能把训练奖励等同于真实任务质量。

**常见追问：** 工具任务如何构造可验证奖励？

**追问参考回答：** 在沙箱验证工具参数、审批规则、测试结果和最终数据库状态，并对越权、重复写入及超预算设惩罚。奖励应对应真实任务成功，不能只奖励调用次数或表面格式，避免模型学会刷分。

### 115. PPO,DPO,GRPO之间的区别，在不同的环境下，它们三个又如何去选？

**面试回答示例：** PPO、DPO 和 GRPO 的选择主要取决于数据与奖励条件。PPO 适合在线采样或交互环境，通常需要奖励信号和价值估计；DPO 直接使用成对偏好数据，适合离线偏好优化；GRPO 通过同一输入的一组输出做相对比较，常见实现省去独立价值网络。没有普遍最优的方法，我会比较奖励可靠性、采样成本、训练稳定性和任务验证能力。最后用独立评测检查效果与风险，而不是只看训练奖励上涨。

**核心回答：** PPO 适合有在线奖励和交互环境的策略优化；DPO 适合已有成对偏好数据；GRPO 适合可组内比较的采样与奖励设置。

**展开要点：** PPO 通常使用采样结果、奖励及价值估计优化策略；DPO 适合已有可靠偏好对的直接偏好训练；GRPO 利用同题多输出的相对奖励，常用于可以打分或验证的任务。选择依据是反馈形式、采样成本、奖励可靠性和基础设施，不是算法名称更先进。Agent 场景先完善工具环境与评测，再判断是否需要训练。

**常见追问：** 如果奖励只有最终成功或失败，如何处理稀疏信号？

**追问参考回答：** 从简单任务逐步增加难度，采样足够候选，并利用可验证的阶段里程碑辅助反馈，但不能偏离最终目标。保留最终状态验收及安全约束；奖励塑形不当会鼓励完成步骤而不完成任务。

## 编码练习与参考实现

附带 `agent_interview_practice.py`，使用 Python 标准库、假模型和临时 SQLite 数据库，运行不需要 API Key。它演示控制流与故障边界，不是供应商 SDK 的直接调用代码，也不执行真实退款。终端执行：

```powershell
python agent_interview_practice.py
```

### 编码题一 实现最小 Agent Loop

**面试回答示例：** 我会先定义模型响应和工具请求的数据结构，建立工具注册表，再实现受预算约束的循环。模型输出最终答案时结束，输出工具调用时校验名称、参数和权限，执行后按调用标识回传观察。未知工具、非法参数和异常都转成结构化错误，而不是直接中断整个服务。验证时用假模型覆盖正常调用、连续调用、错误和步数上限，并检查执行轨迹。真实接入还需适配消息协议、持久化和取消处理。

**要求：** 支持最终回答、一个或多个工具调用、工具注册、参数校验、未知工具错误、执行异常和最大步数；保留调用标识和观察结果。

**参考设计：** `agent_loop()` 注入模型适配器和工具注册表；每次工具观察返回后继续调用模型。模型适配器负责把简化响应与供应商消息协议转换，执行器负责业务权限。工具校验失败返回结构化错误，不执行真实操作。

**验收与追问：**

- 正常工具结果能被模型用于回答，未知工具不会直接崩溃。
- 重复 call_id 被拒绝，不同 call_id 的无限循环仍被步数限制截停。
- 最终回答只是模型输出，业务是否成功仍需独立验收。
- 示例 deadline 仅在步骤之间检查，不能打断阻塞调用；实际模型、HTTP 与工具适配器必须设置剩余 deadline 对应的超时，异步版本还需取消传播。
- 示例工具均为本地纯计算。真实写工具还需要权限、幂等和对账机制，不能把重试放进循环后就认为可靠。

**扩展练习：** 接入项目使用的真实 SDK，保留实际 tool_call_id；增加输出大小限制、总 Token 预算、受控重试和异步工具。提交运行版本及错误样例，不只演示一次成功。

### 编码题二 实现持久化审批与恢复

**面试回答示例：** 我会先持久化操作提议、参数摘要和等待审核状态，让进程重启后仍能找到待审任务。审批入口验证可信身份，并确认批准对应的是原始提议与版本。执行使用稳定幂等键，本地账本和状态更新尽量放在同一事务中。重复审批不能重复产生副作用。验证时覆盖重启恢复、未授权审批、参数修改和重复提交。对外部服务还要增加状态查询与对账，因为本地事务不能包住外部操作。

**要求：** 提议操作后暂停；进程重启后还能审批；批准必须绑定原提议；重复提交不重复产生本地副作用；未授权审批被拒绝。

**参考设计：** `create_pending()` 保存参数与 waiting_review 状态；`approve_and_execute()` 校验可信授权结果与原始提议，使用事务完成本地账本、操作记录和任务状态更新。重新打开同一数据库模拟进程重启。

**验收与追问：**

- 重启后原提议仍存在，重复批准只得到同一结果。
- 提议改变后拒绝旧审批；未授权主体不能批准。
- 使用整数分表示金额，避免二进制浮点误差。
- 示例通过一个 SQLite 事务实现本地原子写入，不能推广为远程 API 的 exactly-once。
- 真实远程调用要先记录 pending 操作，使用外部幂等键，并处理“结果未知”状态；还要实现身份校验、审批有效期、拒绝、取消及参数版本绑定。

**扩展练习：** 模拟对端执行成功后断网，加入查询操作状态和对账流程；模拟两个进程同时批准。LangGraph 版本还需验证 interrupt 恢复时节点前部代码重放的影响。

### 编码题三 实现离线评测器

**面试回答示例：** 评测器会读取固定任务集，为每个样本重置环境，运行 Agent 后独立检查最终输出、调用轨迹和业务状态，再汇总成功数、耗时、调用次数及失败原因。测试数据需要覆盖正常执行、非法工具、权限错误和预算耗尽。程序评分优先用于可验证结果，开放内容再结合证据核查。假模型适合验证控制流，不能代表真实业务成功率；接入真实模型后，还要记录模型版本、Token 和费用。

**要求：** 读取固定任务集、重置环境、运行任务、独立评分并汇总成功数、耗时、调用数量和失败原因。真实模型版本还需统计 Token 与费用。

**参考设计：** `evaluate()` 使用确定性假模型检查正常调用、未知工具处理、非法工具名称和步数限制；`main()` 补充审批恢复及幂等断言。假模型的检查通过率只是程序行为验证，不代表真实模型的业务成功率。

**建议的真实任务格式：**

```json
{
  "id": "refund_requires_approval",
  "user_input": "按政策帮我申请退款",
  "fixture": "eligible_order_without_approval",
  "allowed_tools": ["lookup_order", "lookup_policy", "request_approval"],
  "expected_state": "waiting_review",
  "forbidden_effects": ["refund_before_approval"]
}
```

**验收与追问：**

- 每个 trial 独立重置环境，不能让前一例的账本、记忆和缓存影响下一例。
- 检查真实业务状态和禁用动作，不能仅匹配输出中的“成功”。
- 真实评测对每个任务重复运行，分别报告总体和任务族指标，说明样本量与波动。
- 以成功数为零时不能计算每成功任务成本；没有真实 Token 数据时报告未知，不填零。
- 重放和评测默认使用沙箱或 mock 工具，不重复触发真实业务写操作。

## 系统设计案例

### 案例一 企业知识库客服与退款 Agent

**面试回答示例：** 我会用固定流程控制身份、权限、审批和退款执行，在政策检索与问题理解部分引入模型。知识库按租户和有效版本检索，订单从业务系统查询，退款资格及金额由确定性代码计算。提议经过审批后，执行前再次检查状态，并使用幂等键。超时先查真实结果，证据不足则澄清或转人工。评测覆盖引用准确、越权访问、重复退款和审批失效，最终以订单与账本状态判断是否完成。

**题目：** 支持政策问答、订单查询和退款申请；知识库属于不同租户，退款需要符合政策并经过审批。说明架构、数据流、失败处理与评测。

**先澄清：** 日请求量、峰值并发、允许等待时间、知识更新频率、退款规则与审批主体。没有业务数字时给出待验证假设，不声称方案已达到某个 QPS。

**参考架构：**

```text
用户 → API 与身份校验 → 任务服务 → Workflow / 受控 Agent
                               ├─ 政策检索：权限过滤 → 混合检索 → 重排
                               ├─ 订单工具：可信身份 → 业务权限 → 查询
                               └─ 退款提议 → 持久化审批 → 幂等执行 → 对账
                  状态数据库 / 产物存储 / 事件流 / trace 与审计
```

**核心数据：**

| 对象 | 关键字段 | 约束 |
|---|---|---|
| Run | tenant_id、run_id、version、status、deadline | 所有读取都验证租户和身份 |
| Evidence | document_id、version、位置、有效时间 | 引用指向实际证据版本 |
| Proposal | operation_id、订单、金额、政策版本、参数摘要 | 审批绑定具体提议 |
| Approval | 提议版本、审批人、决定、有效期 | 修改参数后重新审批 |
| Operation | 幂等键、pending/unknown/confirmed、外部交易 ID | 超时后核查真实执行状态 |

**执行流程：**

1. 从可信身份解析租户与用户，判断请求类型；缺少订单或关键条件时澄清。
2. 检索用户可访问的有效政策，查询用户拥有的订单，获取事实证据。
3. 确定性业务代码计算资格和金额；模型负责解释，不独立修改规则。
4. 生成退款提议并等待必要审批，保持 run 与版本可恢复。
5. 执行前再次验证订单状态、政策和审批有效性，使用稳定幂等键调用退款服务。
6. 记录真实结果，结果未知时查询和对账；向用户返回可核验状态，不虚报成功。

**失败与安全：** 无证据时澄清或转人工；政策冲突需确认有效版本；工具超时不默认失败；前端断流后由任务服务决定是否继续。工具结果含恶意指令不能扩大权限；租户隔离贯穿索引、缓存、线程、产物和日志。

**评测与发布：** 构建可答、不可答、冲突政策、越权订单、重复退款、审批失效及注入样本；核查引用、订单最终状态与退款次数。记录成功率、越权次数、p95 延迟及每成功任务成本。灰度按租户稳定分流，影子写调用使用隔离环境。

**面试追问：** 为什么不全部用 Agent？退款工具超时但实际成功怎么办？知识库更新后旧审批是否还有效？如何证明改了 Prompt 后没有增加重复退款？

### 案例二 带人工审核的长文档生成 Agent

**面试回答示例：** 我会先离线解析长文档，保存结构、来源和分层索引，再把报告任务拆成提纲、检索、章节生成和核验。各章节保留证据引用，产物带版本，任务状态持久化。人工审核时暂停执行，收到意见后只重跑相关章节与依赖步骤，保留旧版方便对比。重启后从检查点恢复，导出等操作避免重复执行。验收同时检查事实支持、章节完整性、术语一致和格式，把表达风格与内容正确性分开评价。

**题目：** 根据多份长文档生成报告，支持人工审核、局部修改、进程重启恢复与版本追踪。

**先澄清：** 文件格式、文档质量、报告模板、引用标准、保密级别、可接受耗时，以及用户修改的是事实、结构还是表达。

**参考架构：**

```text
文件摄取 → 解析与校验 → 结构化产物与分层索引
                               ↓
报告任务 → 提纲 → 证据检索 → 章节生成 → 引用与格式校验
                                           ↓
                                     人工审核与修改意见
                                           ↓
                            新分支 → 重跑受影响节点 → 新版报告
```

**节点设计：** 提纲输出章节任务及验收标准；每章输出草稿与证据 ID；校验节点检查数字、引用和模板；导出节点生成文件并视觉检查。只有独立章节并行，跨章口径和全文一致性由汇总节点处理。

**状态与版本：** 保存源文件版本、提纲版本、节点输入摘要、产物 ID、依赖和审批意见。Checkpoint 管执行状态，产物存储保留文件；原文、草稿和最终稿分别存储。节点输出不要把整个报告反复塞进对话。

**局部修改：** 修改某章节时从相应输入版本创建新分支，失效该章及依赖它的摘要、目录和导出文件；未受影响章节可复用。若修改了来源或整体口径，需要重新校验所有受影响章节。外部已发送的旧文件不能因状态回退自动撤销，按业务沟通或发布规则处理。

**恢复与一致性：** 长任务通过队列与持久化状态执行，任务租约或版本控制避免多个 worker 同时恢复。上传或导出采用稳定产物键并校验内容版本；人工反馈绑定具体报告版本。临时文件和失败产物按保留策略清理。

**评测：** 使用人工认可的需求清单检查覆盖率；抽取可核验事实与来源位置，核查数值和引用；检查格式与页面布局；记录修改轮数、恢复成功情况和总耗时。风格评分与事实准确率分开统计。

**面试追问：** DOCX 页码如何稳定定位？源文件更新后如何使旧证据失效？章节并行生成造成术语冲突怎么办？审批暂停前的导出节点会不会重复运行？

## 项目讲述与复习验收

### 项目讲述模板

下面是准备提纲，不是可以冒充的工作经历。

1. **问题与边界：** 服务谁，输入输出是什么，不能做什么。
2. **基线与选择：** 最初使用什么简单方案，什么失败证据支持引入 RAG、Agent 或多 Agent。
3. **你的贡献：** 具体负责哪个模块、设计什么接口和状态，避免将团队成果全部归于个人。
4. **工程挑战：** 举一个真实错误，说明如何复现、定位、修复和验证。
5. **结果证据：** 给出真实任务集、样本量、前后指标与约束；没有测量则说明尚未验证。
6. **取舍与下一步：** 当前限制是什么，为什么暂时接受，如何继续改进。

### 复习验收清单

- 能画出最小 Agent 执行循环，并指出权限和副作用发生的位置。
- 能解释“超时不代表未执行”“Checkpoint 不撤销外部操作”“thread_id 不提供鉴权”。
- 能给 RAG 失败做分层定位，而不是只建议换模型、增大 top_k。
- 能定义任务成功标准并构建错误、权限和恢复评测样本。
- 能解释工具 Schema 与业务校验、线程状态与长期记忆的区别。
- 能运行编码练习并说明它在真实 SDK、分布式执行和权限方面的限制。
- 能用真实项目材料说明设计取舍；没有实践过的协议、框架或训练方法明确说明学习范围。
